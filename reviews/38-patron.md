# R-38 · 후원 선택

[색인](00-index.md) · 계획 `plans/38-patron.md`(삭제됨) · [◀ R-37](37-wire.md) · [◀ R-36](36-shove.md)

## 결론

**통과 · 완료 정의 여섯 전부 충족 · 규칙은 한 줄도 안 움직였다.** 타이틀에서 다섯 중 둘을 고르고, 고른 조합으로 12층을 돌고, 반출한 JSON에 그 조합이 실려 CLI가 같은 조합으로 재생한다. 엔진·데이터·봇·게이트 무변경이므로 `npm run tune`의 수치가 R-36과 **소수점까지 같다** — 그것이 「규칙 불변」의 증거다.

| 완료 정의 | 판정 |
|---|---|
| 선택 — 다섯 중 정확히 둘, 둘이 아니면 시작 불가 | ✓ 토글 다섯(`aria-pressed`) · 셋째를 누르면 가장 오래된 것이 빠진다 · `disabled` |
| 열 조합 — `no fused card`가 어느 조합에서도 안 난다 | ✓ `test/steps.test.ts`가 열 쌍을 다 `runSteps().next()`로 연다 |
| 순서 무관 — 아테나→제우스와 제우스→아테나가 같은 런 | ✓ `patronPair`가 엔진 `gods` 순서로 굳힌다 · 브라우저가 실제로 역순으로 고르고 454결정 기준선을 그대로 낸다 |
| 반출·재생 — JSON에 조합이 들어가고 CLI가 그 조합으로 재생 | ✓ `ReplayFile.patrons` · `readReplay` 검증 · `sim/runner.ts`가 그것을 `run`에 넘긴다 |
| 옛 로그 — `patrons` 없는 replay는 제우스+아테나 | ✓ 선택 필드 + `run`의 기본값. `sim/play.ts`가 쓰는 파일도 그대로 |
| 게이트 — `tune` 하한 하나, 새 지표 없음 | ✓ 하한 0.05 통과 · 조합별 화면 표시 안 만듦 |

`npx tsc --noEmit` 통과 · `npm test` **119**통과(20파일, 116 → 119) · `npm run tune` 하한 0.05 통과·**수치 불변** · `npm run e2e` 통과(시드 589 · 454결정 · 12층 완주 · 조합 토글 클릭 · 반출 `patrons`).

## 만든 것

### 배열을 둘에서 하나로 줄였다 — 계획의 정렬 함정을 테스트가 아니라 삭제로 닫았다

계획 §2는 「`godIds`(데이터 순서)와 `gods`(코드 상수)가 갈릴 수 있다」를 함정으로 적고 **두 배열이 같은지 보는 테스트**를 답으로 냈다. 그런데 `godIds`는 온 저장소에서 **시작 화면 범례 한 곳**에서만 쓰였다. 그래서 테스트를 붙이는 대신 `ui/header.tsx`에서 지우고 토글을 엔진의 `gods`로 그린다:

```tsx
export const patronPair = (picked: readonly GodId[]): PatronPair => gods.filter((god) => picked.includes(god)) as unknown as PatronPair;
```

같은 배열이 화면 순서도 정하고 넘길 순서도 정하므로 **갈릴 자리가 없다.** `data/gods.json`과 `gods`를 대조하는 테스트는 그래도 남겼다 — 이제 정렬을 지키는 것이 아니라 「데이터의 신 id가 `GodId`에 다 있다」를 지킨다(어긋나면 `state.favor[god.id]` 조회가 조용히 빗나간다). `godName`만 데이터에서 온다.

정규화가 실제로 도는지는 두 자리에서 본다: `test/ui.test.ts`가 `run(9, …, patronPair(["artemis","poseidon"])).actions`와 뒤집은 것의 결정열을 대조하고, **브라우저가 아테나→제우스 순으로 고른다**(아래).

### 토글 다섯 — 드롭다운 둘이 아니다

```tsx
setPicked((now) => (now.includes(god) ? now.filter((id) => id !== god) : [...now, god].slice(-2)));
```

`slice(-2)`가 「먼저 해제하세요」를 안 만든다. 기본값은 제우스+아테나라 아무것도 안 고르고 시작하던 사람이 같은 런을 얻는다. 서 있던 `.god-legend`의 `span`이 `button`이 됐고 색 점(`i`)과 이름은 그대로다 — 고른 둘만 불투명하고 테두리가 신 색이다.

**라벨 한 줄을 더 만들었다**(계획에 없다). 다섯 버튼만으로는 그 줄이 아직 범례로 읽힌다 — 「런 시드」와 같은 꼴의 `후원할 신 둘`이 서고 `aria-labelledby`가 그것을 가리킨다. 시작 화면 세로는 **900px 그대로**다(P-26의 눈금, 1440×900에서 세로 넘침 없음).

### 반출 파일이 조합을 든다 — 그리고 재생하는 쪽이 그것을 읽는다

```ts
export type ReplayFile = { seed: number; actions: ReplayAction[]; replay_mode: "action_log"; patrons?: PatronPair };
```

선택 필드다. `readReplay`는 있을 때만 검증한다 — 길이 2 · 서로 다름 · `gods`에 속함, 한 줄. `sim/play.ts`는 계획대로 조합을 안 묻는다(파이프 입력의 자리 수를 안 바꾼다). `sim/replay.ts`가 `sim/engine.ts`를 **값으로** 부르는 첫 자리인데, 반대 방향(`engine` → `replay`)이 타입 전용이라 순환이 안 남는다.

## 계획이 못 본 것

### 배선 표에 재생 쪽 한 줄이 빠져 있었다

계획의 배선 표는 `sim/replay.ts`(타입·검증)까지만 적었다. 그런데 **`patrons`를 파일에 적는 것과 그것으로 재생하는 것은 다른 줄**이다 — `sim/runner.ts:170`이 `run(replay.seed, undefined, replay.actions)`로 부르고 있었다. 그 한 줄이 없으면 반출 파일에 `patrons: ["ares","artemis"]`가 실려 있어도 CLI는 제우스+아테나로 재생한다. 계획이 완료 정의에 적은 바로 그 실패가 검증만 붙이고 끝냈으면 그대로 남았을 자리다.

`tools/e2e.ts`의 CLI 대조도 같은 이유로 `browser.replay.patrons`를 넘긴다.

### e2e가 「제우스+아테나를 명시적으로 클릭」할 수 없었다

계획 §5는 기준선을 지키려고 e2e에 제우스+아테나 클릭을 지시했는데, **그 둘이 이미 기본 선택**이라 그대로 누르면 해제된다. 그래서 껐다 켠다:

```
제우스 클릭 → 하나만 남는다 → 「런 시작」 disabled 확인 → 제우스 다시 클릭 → 다시 눌린다
```

부수 효과가 오히려 이 회차의 제일 좋은 검사가 됐다 — 두 번째 클릭으로 고른 순서가 **아테나→제우스**가 되므로, 정규화가 빠진 날 브라우저는 다른 시작 덱으로 돌고 454결정 완주 기준선이 그 자리에서 깨진다. 화면에는 아무 표시도 안 나는 함정을 e2e가 자동으로 밟는다.

e2e 검사 셋이 늘었다: 조합 토글(다섯 · 막힘 · 되열림 · 눌린 둘), 반출 헤더의 `patrons`, 결과 eyebrow `시드 589 · 제우스 + 아테나 · 12/12층`. 계획이 적은 시드 170은 R-36에서 이미 589로 옮겨졌다(170은 헌신에 못 닿아 `grace`를 안 지난다).

### 결과 화면의 조합은 `result.pairing` 문자열이 아니라 상태에서 온다

기존 결과 화면은 호의 칸을 `result.pairing?.split("+")`로 그렸다. 조합을 화면이 이미 들고 있는데 문자열을 다시 쪼개는 것이 되므로 `ResultScreen`에 `patrons`를 넘기고 eyebrow·호의 칸·반출 셋이 그 하나를 쓴다. `patrons` 상태를 `picked`와 나눈 이유는 `seed`를 `seedInput`과 나눈 이유와 같다 — **돌고 있는 것**과 **입력칸에 있는 것**은 다른 값이다. `reset()`은 계획대로 선택을 유지한다(같은 조합으로 다른 시드가 기본 동작이다).

## 사람이 최저 셀 조합을 고를 수 있게 됐다

계획의 함정 셋째 줄이 이 회차의 진짜 결과다. 지금까지 조합 편차는 **통계**였다 — 봇이 열 조합을 균등히 돌고 그 분산을 `tune`이 보고했다. 이제는 **체감**이다:

| | 조합 | 승률(ε=0, 300런) |
|---|---|---:|
| 최저 | athena+ares | **14.7%** |
| 최고 | poseidon+artemis | **69.3%** |

같은 화면에서 옆자리 버튼 둘을 누르는 것으로 4.7배 난이도가 갈리고, 화면에는 그 사실을 말하는 것이 하나도 없다. **이 회차는 그것을 고치지 않는다** — 밸런스 게이트는 하한 하나 그대로고(CLAUDE.md), 편차를 새 지표로 만들지 않았다. 「추천 조합」이나 승률 표도 안 만들었다: 화면에 승률을 내면 최저 셀을 아무도 안 고르고, 그러면 그 셀은 고쳐질 이유마저 잃는다. 라이벌 조합(제우스+포세이돈 · 아테나+아레스)도 막지 않았다 — 융합 카드가 열 조합에 다 있고 라이벌이라는 것 자체가 난이도 축이다.

편차의 뿌리는 색인의 첫 부채(지속성을 못 재는 토큰 가중치)이고, 이 계획과는 다른 층의 일이다.

## 남은 부채

- **조합 편차가 이제 사람의 선택지다**(위). 최저 14.7% · 최고 69.3%, 화면에는 아무 표시도 없다. 표시를 만드는 것이 답이 아니라 편차를 닫는 것이 답이다
- **CLI로는 조합을 못 고른다.** `sim/play.ts`는 시드만 묻고 `--patrons` 플래그는 안 붙였다(파이프 입력의 자리 수가 바뀌면 기존 스크립트가 다 깨진다). 사람이 CLI로 여러 조합을 돌려 보고 싶어진 뒤의 일이다
- **조합 미리보기가 없다.** 고른 둘의 시작 덱 10장과 융합 카드를 타이틀에서 보여 주는 것 — `godDecks`·`fusionCards`가 이미 export돼 있어 화면만의 일이지만, 시작 화면이 900px 눈금을 넘으면 P-26의 기준이 깨진다
- **`grace_*` 시나리오의 70 호의는 정규화 뒤 언제나 `gods` 순서에서 앞선 신이 받는다.** UI는 시나리오를 안 쓰므로 지금은 무해하다. 시나리오를 화면에 여는 날 결정이 필요하다
- **`logs/shots/1-setup.webp`가 옛 화면이다.** 시작 화면이 바뀌었는데 그 접촉 시트를 만드는 도구가 없다(수동 산출물이다)
