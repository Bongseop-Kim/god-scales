**통과 · 완료 정의 전부 충족 · 계획 하나를 실측이 되돌렸다**

빈 칸이 타입에서 사라졌고(`Lineup = EnemyDefinition[]`), 배포된 `combat`·`elite` 편성 12개가 전부 **4인**이며, 보스가 **칸 0·1 두 칸**에 같은 객체로 선다. 조합 승률 하한 `0.05`는 **안 내리고** 넘었다(최저 셀 0.140 → **0.083**).

## 설계 대조 — 계획대로 된 것

### 1 · `null`을 타입에서 지웠다

`Lineup = (EnemyDefinition | null)[]` → `EnemyDefinition[]`. 딸려 지워진 것 넷: `sim/engine.ts`의 `encounter` `null` 분기와 `lineup.filter(...)` 둘, `tools/validate.ts`의 `slotFailure`·`groupStrength` 분기. `emptySlot`은 남겼다 — 시체와 같은 꼴이라 `hp > 0` 필터가 전부 그대로 돈다.

### 2 · 자리 규칙을 「표」에서 「순서」로

`roleSlots` 표(칸 번호 못 박기)를 순서 규칙 세 줄로 바꿨다.

```ts
const roles = [enemy.id, ...rest].map((id) => enemies.find((c) => c.id === id)?.role ?? "");
const back = roles.findIndex((role) => backRoles.includes(role));
return back >= 0 && roles.slice(back).some((role) => frontRoles.includes(role));
```

반려 키 `slot_scope`는 그대로다 — **새 실패 종류를 안 만들었다.** 값이 실제로 나왔다: 저승 6편성이 「앞 셋 + 뒤 하나」 셋과 「앞 둘 + 뒤 둘」 셋으로 갈렸고, 표를 지켰다면 칸 2·3이 여섯 번 다 압박+광신도였을 것이다.

계획이 「뿌리는 앞줄이어야 한다는 계약이 순서 규칙의 첫 항으로 따라온다」고 적은 것은 **절반만 맞다** — 뒷줄 역할이 뿌리인 편성은 그 **뒤에 앞줄이 설 때만** 걸린다. 뒷줄 넷으로만 짠 편성은 순서 규칙을 통과한다. 배포 데이터에는 없고 `count [4,4]`와 밴드가 따로 잡으므로 규칙을 늘리지 않았다.

### 3 · 보스는 같은 객체를 두 칸에

계획의 안 A를 그대로 썼다. 대가는 「중복 제거 다섯 줄」이 아니라 **여섯 줄**이었다 — 계획이 센 네 곳(`endTurn`·출혈·`spite`·`rally`)에 둘이 더 있다:

- `core/favor.ts`의 `targets()` — 진노의 `all_enemies` 개입이 보스를 두 번 친다
- `sim/bots/rule.ts`의 `intent()` — 봇이 보스전에서 들어오는 피해를 두 배로 읽고 방어만 쌓는다

여섯을 인라인 `[...new Set(...)]` 여섯 벌로 두는 대신 `core/combat.ts`에 한 줄을 뒀다:

```ts
export const actors = (combat: CombatState): EnemyState[] => [...new Set(combat.enemies)];
```

이유를 여섯 번 적지 않기 위해서다. **칸이 필요한 쪽은 배열을 그대로 읽는다** — `EnemyState.slot`은 안 만들었고 칸은 여전히 배열 인덱스 하나다.

`livingInReach`는 `actors`를 안 쓴다. **걸러 낸 뒤에** 지워야 사거리 `1`이 보스에 닿는다:

```ts
return [...new Set(combat.enemies.filter((enemy, slot) => enemy.hp > 0 && slots.includes(slot)))];
```

먼저 지우면 `indexOf === slot`인 칸 0만 남아 뒷줄 카드가 보스전에서 죽는다. 이 한 곳이 `resolveTargets`·`resolveChainTargets`·`canReachTarget`·`guardFor`·`firePowers`를 전부 덮는다.

### 5 · 화면

`EnemyView`에 `span`을 싣고 별칭을 **동일성으로 한 번만** 내보낸다. 화면은 `span > 1`이면 `grid-row: span 2`를 인라인으로 붙이고(폭이 데이터라서 CSS 클래스로는 못 든다) 덮인 칸의 자리표시를 건너뛴다 — 안 건너뛰면 판이 다섯 칸이 된다. `slotLabel`이 「칸 0~1 앞」을 읽는다.

`.enemy.wide { min-height: 220px }`가 필요했다. **`grid-row: span 2`만으로는 아무것도 안 커진다** — `.enemy-panel`의 행이 자동 크기라 남는 둘째 행 높이가 0이고, 그러면 판이 두 칸이라는 사실이 화면에 없다.

## 밸런싱 — 계획 §5가 틀린 자리

계획: 「개체 체력 대략 절반 → `tune` → `enemyDamageScale`을 **한 번** 조정 → 다시 `tune`. 손잡이는 둘, 게이트는 하나.」

**게이트는 정말 하나였다.** 하한 `0.05`는 두 번째 측정에서 넘었고 한 번도 안 내렸다. 회차를 잡아먹은 것은 기존 테스트에 이미 있던 **집계 지표 여섯**이다. CLAUDE.md가 「통과 못 하는 값을 깎지 않는다」라 하나도 못 건드렸고, 그것들이 서로 반대 방향을 당겼다.

| 지표 | 어디 | 밴드 | 방향 |
|---|---|---|---|
| 조합 승률 하한 | `test/matrix.test.ts` | ≥ 0.05 | 쉬울수록 좋다 |
| `grace_slots_filled` | `test/grace.test.ts` | > 1 | **쉬울수록** |
| `grace_milestones[6]` | `test/grace.test.ts` | > 0 | 쉬울수록 |
| `low_rest_clear_rate` | `test/map.test.ts` | < 0.24 | **어려울수록** |
| `block_efficiency`(500) | `test/enemies.test.ts` | [0.80, 0.93] | **어려울수록** |
| `block_efficiency`(층화 2000) | `test/freeze.test.ts` | [0.74, 0.88] | 어려울수록 |
| `winRate`(층화) | `test/freeze.test.ts` | [0.15, 0.70] | — |

`block_efficiency`는 **한 턴 피해**를 재고 `grace_slots_filled`는 **런 전체 누적 피해**를 잰다. 조우가 길어지면 앞은 내려가고(쌓은 방어가 버려진다) 뒤도 내려간다(칩 피해가 헌신을 무너뜨린다). 계획대로 총 체력을 남기면 **둘이 같이 깨진다.**

**`damage` 두 줄이 안 움직인 것이 이번 데이터 작업의 판정이다** — 개체 damage를 인원이 늘어난 만큼 정확히 내리면 4인 합이 옛 밴드 안에 그대로 들어온다. `hp`가 움직인 이유는 위 격자다: 총 체력을 남기는 값이 지표를 깬다. 하한도 같이 내린 것은 `floorCeiling`이 1층 상한을 밴드 **가운데**로 잡기 때문이다 — 하한을 두고 상한만 내리면 1층에 놓을 4인 편성이 하나도 없다.

## 계획에 없던 것

### 못 잰 것 — 트리에 다른 계획이 살아 있었다

작업 내내 `plans/44-cards.md`(P-44 · 카드가 늘어난다)의 **미커밋 변경**이 같은 파일 셋에 있었다. 사용자가 「현재 트리에서 그대로 진행」을 골랐고, 겹치는 파일은 전부 부분 편집으로만 건드려 P-44 작업물을 안 덮었다.

P-44가 `data/enemies.json`에 넣은 것을 **그대로 보존했다**(패턴 행동만 살리고 값만 갈아 끼우는 스크립트로 패치했다): `drain` 셋 · `fog` 둘 · 저승 방패병의 `bulwark 2 all_allies` · 지상 방패병의 `thorns 1 self` · 지상 전령의 `frenzy` 대상이 `ally` → `all_allies` · 보스 패턴 넷째 칸(`favor_shift -3` · `drain 2`).

**그래서 위 「후」 숫자는 P-41 단독의 값이 아니다.** 「전」은 커밋 `0773d41`이고 「후」는 P-41 + P-44 미커밋분이다. 특히 헌신 비율 0.134 → 0.061의 절반이 어느 쪽 몫인지 이 트리에서는 못 가른다.

### 지운 것 — `staging/enemies-underworld.json`의 열넷

배포된 적 열넷을 이름만 바꿔 베낀 파일이었다. 밴드가 움직일 때마다 같은 데이터를 두 곳에서 고치게 하는데, 그 픽스처를 읽는 테스트의 단언은 **한 줄**이다(「밴드 밖 편성 하나를 반려한다」). `enemy_bad_group` 하나만 남겼다 — 400줄 → 24줄.

`core/__fixtures__/broken/11-passive.json`은 반대로 **키웠다.** 1인 편성이라 새 `count [4,4]`가 첫 판정에서 `value_outlier`로 잡아 버려, 그 픽스처가 지키던 「반려된 적의 편성을 가리키는 층」 경로(둘째 판정의 `map_layout`)를 한 번도 안 지났다. 4인 · 밴드 안으로 고쳐 그 경로를 되살렸다.

### 시드 하나를 다시 골랐다

`test/demands.test.ts`의 「첫 요구를 수락해도 조건이 안 맞는」 시드 2 → **9**. 판에 넷이 서면 「셋을 쳐라」가 쉬운 약속이라 시드 2의 첫 요구가 지켜지는 쪽으로 넘어갔다. 그 테스트가 회차마다 하던 일(3 → 4 → 2 → 9)과 같다. 400시드를 훑어 다섯 단언을 다 만족하는 시드 목록을 뽑았다 — 첫 블록의 시드 4는 이번에도 살았다.

## 남은 부채

- **조합 편차가 1.5배가 됐다.** 변동계수 0.444 → **0.540**, ⚠ 0 → **3**. 4인 조우는 광역·연쇄에 유리하고 단일 대상에 불리한데 `tools/value.ts`가 그 차이를 못 잰다 — B-0 3번(분산 감소)과 반대 방향이고, 색인의 「토큰 가중치가 지속성을 구분하지 못한다」와 같은 뿌리다
- **판을 꽉 채워도 사거리는 안 움직인다(+0.5%p).** 뒷칸에 늘 누가 서 있는 지금도 낸 카드의 95.2%가 기본값이다. 이제 「봇이 자리를 값으로 안 읽는다」에 값이 붙었다 — 자리 콘텐츠를 더 만들기 전에 `chooseTarget`·`chooseCard`에 자리 항을 붙이는 것이 먼저다
- **요구 임계가 1.7인 조우에 맞춰져 있다.** 헌신 비율 0.134 → 0.061이고 은혜 슬롯 1.37 → 1.02다. 4인 조우는 `damage_taken`을 올리고 `hit_targets_in_turn`을 올린다 — 아테나·아르테미스의 「적게 맞아라」는 어려워지고 제우스의 「셋을 쳐라」는 공짜가 됐다. 색인이 R-29에서 「천장은 열렸다, 다음 회차 자리다」로 남긴 그 줄이고, **이번 회차가 그것을 급한 것으로 만들었다**
- **보스가 혼자 서고 칸 2·3은 비어 있다.** 계획대로다 — 두 칸을 차지하는 것만으로 사거리 `1`·`12`·`01`이 보스전에서 처음 살았다. 부하를 붙이면 보스 층 편성 데이터·밴드·재측정이 딸려온다
- **집계 지표 일곱이 서로 반대를 당긴다.** 이번에 그 사실이 처음 값을 청구했다(격자 25점). `block_efficiency` 두 줄은 같은 것을 두 표본으로 재고, `grace_slots_filled`와 `low_rest_clear_rate`는 난이도의 같은 축을 반대 부호로 잰다. 밸런스 게이트는 하나여야 한다는 CLAUDE.md의 규칙과 테스트에 남은 옛 밴드 여섯이 부딪히는 자리다
