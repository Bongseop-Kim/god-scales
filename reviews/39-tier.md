## 결론

**통과 · 완료 정의 하나 미달 — 「지상 일반 전투 3택1 중 한 자리 tier2」를 실측이 되돌렸다.** 값에 계단이 셋 생겼다: tier1 `[4, 8)` 124장 · tier2 `[8, 10)` 15장 신규 · tier3(융합) `[10, 13]` 10장. **밴드가 반개구간이라 경계값이 한 칸에만 든다** — 옛 판은 patron `[4, 8]`과 융합 `[6, 10]`이 6~8에서 겹쳐 융합 열 장 중 **여섯이 patron 밴드 안**이었다(아레스+제우스 6.00이 최고 patron 카드 7.5보다 약했다). 융합 여덟 장을 올려 열 장이 전부 10 이상이다. **배포된 124장은 한 줄도 안 바뀌었다** — 그것이 이번 회차의 대조군이고, 덕분에 승률 변화를 원인 둘로 갈라 잴 수 있었다:

## 만든 것

### 밴드는 배열 하나고 판정은 반개구간이다

`isValueAllowed`의 하드코딩된 2티어(`card.patron_pair ? [6, 10] : [4, 8]`)를 밴드 셋으로 일반화했다:

```ts
const valueBands: [number, number][] = [[4, 8], [8, 10], [10, 13]];
export const cardTier = (card: Pick<Card, "patron_pair" | "tier">): number =>
  (card.patron_pair ? valueBands.length : card.tier ?? 1);
export function isValueAllowed(card: Card): boolean {
  const tier = cardTier(card);
  const band = valueBands[tier - 1];
  if (!band) return false;
  const value = expectedValue(card);
  // 꼭대기 칸만 상한을 포함한다 — 그 위에는 밴드가 없어서다
  return value >= band[0] && (tier === valueBands.length ? value <= band[1] : value < band[1]);
}
```

**융합은 `tier`를 안 적는다** — `patron_pair`가 곧 3이고, 스키마가 그것을 잠근다(`tier`는 1·2만, 융합에는 금지). 그래서 등급이 두 곳에 적히는 자리가 아예 없다. `cardTier`의 인자를 두 칸(`patron_pair`·`tier`)으로 좁혀 **화면도 같은 함수를 부른다** — 「게이트는 상급인데 화면은 아니다」가 생길 자리를 삭제로 닫았다(P-38이 `godIds`를 지운 것과 같은 수법).

경계에 카드가 몰려 있다는 계획의 경고는 실측으로 확인됐다: tier1 최고가 **7.50**이라 문턱 8은 아무도 걸터앉지 않는다. tier1 평균 5.249 대비 tier2 평균 8.496은 **1.62배**, tier3 10.63은 **2.02배**다.

### 풀 게이트는 tier마다 평균을 내고, 비율은 안 가른다

```ts
export const poolValueMax: Record<number, number> = { 1: 5.5, 2: 9 };
```

`poolRejects`의 걷어내기 루프는 하나로 뒀다. 비율은 그 신의 **풀 전체**(tier 무관) + 은혜 tier4를 보고, 장당 기대값은 **tier마다** 본다:

```ts
const heavy = Object.keys(poolValueMax)
  .map((tier) => pool.filter((card) => cardTier(card) === Number(tier)))
  .find((step) => step.length > 0 && poolStat(step).average > poolValueMax[cardTier(step[0])]);
```

**계획 §4의 두 문장이 서로 어긋났다**: 「완화 비율은 티어를 안 가른다」와 「tier2 세 장은 tier1 풀의 비율 계산에서 빠져야 한다」. 뒤쪽을 그대로 따르면 tier2 15장이 비율 규칙에서 **완전히 면제**된다 — 한 신이 값 8~10짜리 완화 세 장을 넣어도 상한 0.30이 못 본다. 그래서 앞쪽(신의 성격은 등급이 아니다)을 골랐다. 결과적으로 계획의 함정(「포세이돈 tier2가 완화로 막힌다」)이 **살아 있는 규칙**이 됐고, 그 함정이 지시한 대로 포세이돈·아테나 tier2를 비완화로 설계했다. 비율은 오히려 다 내려갔다(비완화 값이 분모에 들어가서다):

| 신 | 비율(P-38) | 비율(P-39) | tier1 평균 | tier2 평균 |
|---|---:|---:|---:|---:|
| 제우스 | 0.274 | **0.238** | 5.424 | 8.333 |
| 포세이돈 | 0.288 | **0.243** | 4.962 | 8.444 |
| 아테나 | 0.287 | **0.254** | 5.249 | 8.500 |
| 아레스 | 0.133 | 0.110 | 5.139 | 8.533 |
| 아르테미스 | 0.139 | 0.116 | 5.394 | 8.667 |

`validate` 리포트의 `pools`도 행을 `신:tier`로 갈랐다 — 한 행으로 섞으면 `average`가 어느 상한과도 안 맞는 숫자가 된다.

`graceBaseline = 3.06`은 **주석 한 줄만 고쳤다**(「tier1 풀만」). 계획 §5대로 다시 재지 않았다 — `expectedValue` 평균 ×0.5는 전체 2.64 · tier1 2.56으로 둘 다 3.06이 아니라, 재정의하면 은혜 45줄이 조용히 흔들린다.

### 획득은 갈래가 정한다 — tier2를 먼저 뽑는다

```ts
const tier2Slots = (path: MapNodeType): number => (path === "elite" || path === "boss" ? 3 : 0);
```

`rewardOffer`가 자리 수를 받아 **tier2를 먼저** 뽑는다. 순서가 곧 결과인 이유는 같은 `createRng(seed * 1000 + nodeSeed)` 스트림을 쓰기 때문이고, 그래서 **자리가 0인 저승 보상은 P-39 이전과 카드열이 완전히 같다** — 테스트가 옛 구현을 열 줄로 다시 써서 조합 셋 × 시드 20 × nodeSeed 18 = 1,080자리를 대조한다(측정 때는 4,320자리까지 돌렸고 전부 일치했다). tier2 15장이 전량 신규라 「`tier`가 없는 patron 카드」가 곧 그때의 후보 배열이라는 것이 이 대조의 열쇠다.

후보 부족 가드도 티어별이다 — 정예·보스가 세 자리를 요구하는데 조합의 tier2 합이 셋 미만이면 `while (offer.length < 3)`이 영원히 돈다. 배포 데이터로는 만들 수 없는 상황이라(신별 3장 × 2신 = 6) 테스트는 자리 수를 7로 요구해 그 가드를 태운다.

**`depth`를 안 읽는다.** 계획의 「깊이가 정한다」가 실측에서 되돌아간 결과이고, 그래서 저승이 tier1뿐인 것은 이제 규칙이 아니라 **데이터**가 든다: `data/map.json`에 저승 정예 편성이 없다(`group_under_forcing`이 「정예는 같은 층 combat보다 세다」를 못 넘은 R-25의 자리). **저승 보스는 tier2 세 장을 준다** — 계획의 표도 「보스 전부, 런당 2회」였으니 의도대로다. 노출은 런당 1~3회(저승 보스 1 + 지상 정예 0~2 + 지상 보스 1)다.

### 화면 — 등급은 이름 앞 칩

`ui/card.tsx`가 `cardTier`를 불러 tier ≥ 2에만 칩을 붙인다(2 = 「상급」 · 3 = 「융합」). 우상단 배지 슬롯은 이미 파워·전체의 것이고 **등급은 그 둘과 직교**하므로 자리를 다투게 두면 하나가 사라진다 — 이름 줄 앞에 세웠다. 색(`--frame`)은 얹지만 뜻은 글자가 다 든다(R-26의 채널 규칙).

## 계획이 못 본 것

### 지상 일반 전투 한 자리가 최저 셀을 깎았다 — 이 회차의 발견

계획 §3은 「정예·보스 전용이면 노출이 런당 2~4회에 그친다」를 이유로 지상 일반 전투에 한 자리를 줬다. 3000런 층화가 그것을 되돌렸다(결론의 표). 자리 수를 3으로 늘려도 최저 셀은 0.090에 머문다 — **자리 수가 아니라 「지상 일반 전투에 tier2가 뜨는가」가 부호를 정한다.**

셀 단위로 보면 원인이 좁혀진다. 계획 §3판(지상 일반 한 자리)에서 **아레스 셀 넷이 전부 내려갔다**: zeus+ares 0.193 → 0.167 · poseidon+ares 0.567 → 0.400 · athena+ares 0.147 → 0.083 · ares+artemis 0.553 → 0.477. 반대로 poseidon+athena는 0.310 → 0.430으로 올랐다. 가설은 값 표와 봇 정책의 합작이다:

- `expectedValue`가 **값싼 자기 강화**를 실제 세기보다 높게 잰다 — `frenzy`·`crit`·`thorns`는 스택당 1.5~4를 받고 `self_damage`는 ×−1.2로만 깎인다. 「광란의 돌진」(피해8+광란2−자해2, 8.6)은 체력이 이미 낮은 아레스 런에서 값이 아니라 빚이다
- `chooseReward`가 **같은 표로** 고르므로 3택1에 tier2가 한 장 섞이면 그것이 언제나 최고값이고, 나머지 두 자리는 장식이 된다 — 「3택1」이 「1택1」이 된다
- tier2 풀이 신별 3장뿐이라 지상 보상 넷이 **같은 카드를 반복해** 덱에 쌓는다(`rewardOffer`의 중복 배제는 한 판 안이다)

정예·보스는 세 자리를 다 tier2로 채우므로 **세 장 중 고르는 결정이 남고**, 그 자리가 런당 1~3회뿐이라 같은 카드가 쌓이지 않는다. 그래서 같은 카드 열다섯 장이 자리에 따라 부호가 반대로 나온다.

### 봇 실측은 사람 승률의 상한이 아니었다

계획의 함정은 「tier2가 섞이면 `expectedValue` 정렬이 언제나 그것을 고르므로 실측은 **상한**이다」라고 적었다. **반대다.** 「항상 고티어를 집는 사람」의 승률이 tier1만 보던 판보다 **낮다**(0.399 → 0.369). 등급을 보고 무조건 집는 것이 손해인 카드가 있으므로, 함정 카드를 알아보는 사람은 봇보다 잘한다 — 이번 실측은 **하한**이다. P-36의 하한과 같은 방향이고, 뿌리도 같다(봇이 값 표 하나로만 고른다).

### `card_win_delta`는 tier2를 못 잰다

배포판 3000런에서 tier2 15장의 `card_win_delta`가 **전부 양수**(0.036~0.216)다. 그런데 그 카드를 뿌리면 승률이 내려간다. 이유는 생존 편향이다 — tier2는 정예·보스 보상에서만 나오므로 **저승을 지난 런만** 그것을 든다. 지표가 「그 카드를 든 런은 잘 이긴다」를 말하는데 실제로는 「잘 이기는 런이 그 카드를 든다」다. 원장의 부채(「주력 카드를 못 잰다」)에 **획득 위치가 곧 교란**이라는 항목이 하나 더 붙는다.

### 배포된 카드는 129장이 아니라 134장이었다

계획의 모든 숫자가 129(patron 119 + 융합 10) 기준인데 실제는 134였다 — P-35·P-36이 자리 조건 카드 다섯을 넣었고 계획을 쓸 때 그 다섯이 빠졌다. 그래서 tier1은 119장이 아니라 **124장**이고 배포 총량은 **149장**이다. 신별 평균·비율은 계획이 적은 값과 실측이 소수점까지 같았다(제우스 5.42 · 아르테미스 5.39 · 아테나 5.25 · 아레스 5.14 · 포세이돈 4.96).

### e2e 시드가 또 죽었다 — 589 → 371

**시드 589는 더 이상 완주하지 않는다.** 정예·보스가 tier2 세 자리를 주자 e2e의 클릭 정책(비용 → 피해 → id)이 다른 카드를 집고, 그 덱이 저승은 지나지만 6조우째에 죽는다. 시드 주석이 예고한 그대로다(「정책이나 콘텐츠가 바뀌면 다시 찾아야 한다」).

첫 시도에서 `npm run e2e`가 **Aside 데몬 미가동**으로 실행되지 않아(`fetch failed: other side closed`) 시드를 먼저 헤드리스로 골랐다 — e2e의 클릭 정책을 스크래치패드에서 흉내내 800시드를 훑었고, 완주 + 여덟 화면을 다 지나는 것이 다섯이었다(56 · 106 · 241 · 371 · 400). 가장 짧은 **371**을 골랐고 **브라우저가 그 값을 소수점까지 확인했다: 330결정.** 옛 다섯 중 56·241도 이번에 완주하므로 371이 죽는 날의 다음 후보다.

**두 번째 시도는 통과했다** — 그 사이에 [P-41](41-cardface.md)이 들어와 드라이버가 클릭당 1초를 버리던 자리를 고쳤다(같은 런 96초 → 17초). 첫 실패가 데몬 부재였는지 그 지연이었는지는 이제 갈라 잴 수 없다.

### `deflect`는 여전히 집이 없다

R-28이 「아테나의 `deflect`(무게 10)는 어느 슬롯에서도 은혜가 못 된다」를 남겼다. tier2가 그 집이 될 수 있는지 재봤다: 비용 1 `deflect` 한 장이 값 **10.0**이라 tier2 밴드 `[8, 10)` 위로 나가고, 비용 2로 낮추면 밴드에는 들어오지만 값이 전부 완화라 아테나 비율(0.254 → 0.296)이 상한에 붙는다. **tier2도 집이 아니다.** 무게 10짜리 토큰 하나는 tier3(융합)에서만 설 수 있다.

### 12층 보상 낭비가 눈에 띄게 커졌다

계획대로 안 고쳤다(고치면 e2e 기준선이 움직인다). 다만 지상 보스가 이제 **tier2 세 장**을 주고 그 자리는 런이 끝나는 자리다 — 낭비의 크기가 「tier1 3장」에서 「tier2 3장」이 됐다. 다음 회차에서 `offerReward` 호출 하나를 빼는 것이 그대로 남아 있다.

## 남은 부채

- **최저 셀을 못 올렸다**(0.147 → 0.140). 티어는 편차를 줄였지만(변동계수 0.489 → 0.444) 바닥은 그대로다 — athena+ares는 여전히 최고 셀(poseidon+artemis 0.737)의 5분의 1이다. 뿌리는 원장의 「토큰 가중치가 지속성을 구분하지 못한다」고 티어는 그것을 안 건드렸다
- **값 표가 자기 강화와 조건·사거리를 못 잰다.** tier2 15장이 그것을 새로 드러냈다 — 「후열 관통」은 뒤 한 칸(`reach: "3"`)만 때리는데 값 9.0이고, R-35는 사거리 `3`이 실플레이의 0.0%라고 적었다. 봇이 값으로만 고르므로 이 어긋남이 곧 승률이 된다. 획득 자리를 정예·보스로 좁혀 **크기를 줄였을 뿐 원인은 그대로다**
- **tier2 풀이 신별 3장이라 반복이 구조적이다.** 정예·보스는 세 자리를 다 채워 한 판 안 중복은 없지만, 런 하나가 정예 둘을 밟으면 여섯 자리에 같은 세 장이 두 번 뜬다. 계획대로 「늘리는 것은 실측 뒤」이고, 실측은 「지상 일반에 뿌리려면 풀이 더 커야 한다」를 가리킨다
- **저승의 등급이 데이터에 의존한다.** `tier2Slots`가 갈래만 보므로 저승에 정예 편성을 놓는 날 저승도 tier2를 준다. 그것을 막고 싶으면 규칙이 다시 깊이를 읽어야 한다 — 지금은 안 읽는 것이 실측에 맞다
- **12층 보상 낭비의 크기가 커졌다.** 위 §12층
