# P-62 · 강화 표현과 바뀐 수치 강조

관련 [R-44](../reviews/44-cards.md) 강화 규칙 · [R-26](../reviews/26-hud.md) 채널 규칙 ·
[R-55](../reviews/55-battle-stage.md) 카드 면 채널 넷 · [WRITING.md](../WRITING.md) · [UI.md](../UI.md)

## 배경

강화는 규칙에 다 들어 있는데 **화면에 거의 안 보인다.** 지금 표현의 전부는 `upgraded()`가 이름 끝에
붙이는 `+1` 두 글자다(`core/rules.ts:96`) — 카드 면의 그림·틀·효과 줄은 강화 전과 픽셀 하나 다르지
않다. 쉼터에서 「카드 강화」를 고르면 **무엇이 얼마나 커지는지 모른 채** 덱을 고른다.

토큰도 같은 자리다. 위력 3이 붙은 채로 「피해 6」 카드를 들면 실제로는 9가 나가는데, 카드에는 계속
6이 적혀 있다. 화면만 보고 이번 턴을 계산할 수 없다.

## 확인한 사실

- `upgraded(card, level)`(`rules.ts:96`)이 정본이다: 규칙은 `damage·block·heal·chain` 넷을 ×1.4
  올림(`grow`), 그 위를 19장의 `upgrade` 델타가 덮는다. 상한은 `MAX_UPGRADE = 2`.
- **원래 값의 출처는 `data/cards.json`이다** — 그것이 base 카드의 정의 자체다. `ui/shared/card.tsx:18`이
  이미 그 파일을 읽어 `cardFace`(그림·신·태그·등급)를 만든다. 규칙을 다시 계산하는 것이 아니라
  **원문을 읽는 것**이라 두 번째 진실이 아니다.
- 손패의 `CardView.effects`는 **은혜가 붙은 뒤**다(`sim/engine.ts:477`, `cardEffects`가 `[...card.effects,
  ...graced]`로 **뒤에 잇는다**). 그래서 base와의 대조는 앞에서부터 인덱스로 맞고, 뒤에 남는 것이 은혜다.
- `dealDamage`(`rules.ts:163`)의 보정은 **공격자 쪽 넷 · 대상 쪽 둘**로 갈린다:
  공격자 = 치명 ×2 → 위력 +스택 → 광란 +2 → 침수 −1. 대상 = 감전 +스택 → 표식 ×1.5.
  **공격자 쪽 넷은 대상이 누구든 같다** — 대상을 고르기 전에도 참이다. 대상 쪽 둘은 아니다.
- `damage`와 `chain` 둘 다 `strike` → `dealDamage`를 탄다(`:387`·`:404`).
- **파랑은 이 게임에서 해로움이다**(`--bane: #6ea8d8`, R-26의 진영색). 오른 수치를 파랑으로 칠하면
  「해로운 것」과 같은 색이 된다 — 강화·버프는 이로움 쪽(`--boon: #e8c377`)으로 간다.
- 쉼터의 `rest_card`는 **제거와 강화가 같은 화면**이다(`choices.tsx:88`) — 화면은 둘을 구별할 수단이
  없다(`options`가 덱 전체일 수도 있어 길이로도 못 가른다). App은 직전 답을 `actions`에 이미 들고 있다.

## 단계

### 1. 공격자 보정을 한 함수로 (`core/rules.ts`)

`dealDamage` 안의 넉 줄을 순수 함수로 뽑고 **`dealDamage`가 그것을 쓴다.** 두 벌을 만들지 않는다:

```ts
/** 공격자 쪽 보정 넷. 대상이 누구든 같으므로 카드 면이 미리 보여줄 수 있는 유일한 몫이다 */
export const attackPreview = (mods: { crit?: number; might?: number; frenzy?: number; soaked?: number }, amount: number): number => { ... }
```

`dealDamage`는 지금처럼 `consumeToken`으로 소모한 **결과를** 이 함수에 넘긴다 — 소모 순서도 산술
순서도 안 바뀐다. 화면은 소모 없이 플레이어의 현재 토큰을 그대로 넘긴다.

**되돌아오는 값이 같은지 보는 테스트 하나**를 남긴다(토큰 조합 몇 벌 × 값 몇 개).

### 2. 카드 면 — 「원래 값 → 지금 값」 (`ui/shared/card.tsx`)

`Effect`(`:142`)가 값 하나를 그린다. 그 자리에 규칙 하나를 더한다:

> **원래 적힌 값과 지금 나갈 값이 다르면, 원래 값을 취소선으로 앞에 두고 지금 값을 크게 세운다.**

원래 값 = `data/cards.json`의 base 카드 그 효과의 `value`/`stacks`.
지금 값 = `CardView`가 실어 온 값(강화 반영) → 여기에 §1의 `attackPreview`(피해·연쇄만).

**중간 단계는 안 적는다** — 6 → 8 → 11을 다 적으면 140px 카드가 숫자 밭이 된다. 사람이 알아야 하는
것은 「카드에 적힌 값」과 「지금 누르면 나갈 값」 둘이다.

```
피해 ~~6~~ 11
```

색: 오른 값 `--boon` 계열, 내린 값(침수) 경고색 `#eb887d`, 취소선은 흐린 회색.
**색만으로 말하지 않는다** — 취소선 자체가 흑백에서도 남는 채널이다(R-26).

`GameCard`에 선택적 `boost?: Tokens` 하나가 는다. 넘기는 자리는 **전투 화면의 손패·무대 둘뿐**이다
(`combat.tsx`의 `FanCard`·staged) — 덱 오버레이·보상·쉼터·결과는 토큰이 없는 자리라 안 넘긴다.
안 넘기면 강화분만 비교한다.

### 3. 강화 카드의 얼굴

`+N`이 이름 끝 글자로만 있는 것을 배지로 올린다 — 등급 칩(`.card-tier`, `:189`)과 **같은 줄, 다른
슬롯**이다(등급은 카드가 태어난 계단이고 강화는 이 런에서 키운 것이라 직교한다).

- 이름의 `+1`은 캡션에서 **뗀다**(`card.name`을 그대로 쓰되 표시에서 접미사를 배지로 옮긴다).
  이름 최대 7자 규칙(WRITING.md)에 `+1`이 더 붙어 두 줄이 되는 것도 여기서 닫힌다.
- 프레임(`--frame`)은 안 바꾼다 — 그 색은 신의 것이다.

### 4. 쉼터 미리보기 (사용자 항목 3)

`RestScreen`이 지금 「어느 카드를 고를까요?」 아래에 덱을 깐다. 강화일 때만 각 카드가 **강화 후**를
같이 보여준다 — §2의 표기 그대로(`~~7~~ 10`), 즉 **고르기 전과 고른 뒤가 같은 얼굴**이다.

값은 `upgraded(base, level + 1)`로 **같은 규칙 함수**를 불러 만든다(재구현 금지).

제거인지 강화인지는 App이 넘긴다 — `actions.at(-1)?.choice`가 직전 `rest` 답이고, `rest_card`는
그 답 바로 다음 결정이다. App은 그 배열을 반출용으로 이미 들고 있으므로 **새 상태가 아니다.**
`heal`은 `rest_card`를 안 지나므로 갈래가 둘뿐이다.

### 5. 어디에나 같은 얼굴

`GameCard` 하나를 고치므로 덱 오버레이(P-53)·보상·승부 카드·결과의 「낸 카드」가 자동으로 따라온다.
**그것이 이 계획이 컴포넌트를 고르는 이유다** — 화면마다 강화 표기를 만들면 다섯 벌이 된다.

## 하지 않는 것

- **규칙·값 불변.** `upgradeScale`·`MAX_UPGRADE`·19장의 `upgrade` 델타를 손대지 않는다. 강화가 세거나
  약하다는 판단은 밸런스 게이트(조합 승률 하한)의 일이고 이 계획은 화면만 만진다.
- **대상 쪽 보정(감전·표식)은 카드에 안 적는다** — 대상을 고르기 전에는 거짓이 되고, 고른 뒤에 숫자가
  또 바뀌면 그게 더 나쁘다. 그 둘은 적 발밑 배지와 툴팁이 이미 말한다.
- 중간 값(base → 강화 → 토큰) 삼단 표기 없음.
- 쉼터에 정렬·필터·미리보기 토글 없음. 덱은 지금처럼 한 줄 7장 그대로 깔린다.
- 강화 애니메이션 없음 — 승부 정산의 뒤집기(`bet-flip`)가 이미 그 자리를 갖고 있고, 쉼터는 화면이
  바로 넘어간다.

## 완료 정의

- 손패의 카드가 위력·광란·치명·침수를 반영한 **지금 나갈 피해**를 보여주고, 원래 값이 취소선으로 남는다.
- 강화된 카드는 어느 화면에서든 `+N` 배지와 바뀐 수치를 들고 선다.
- 쉼터에서 강화를 고르면 후보마다 「7 → 10」이 보이고, 그 값이 실제로 덱에 들어간 값과 같다.
- 파랑을 강조색으로 쓰지 않는다 — 진영색 규칙이 안 깨진다.
- `attackPreview`와 `dealDamage`가 같은 값을 돌려준다(테스트).
