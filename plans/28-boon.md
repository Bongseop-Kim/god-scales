# P-28 · 은혜 (하데스 2식)

`plans/28-boon.md` · [◀ P-30](30-intervention.md) · [색인](../reviews/00-index.md) · [P-29 ▶](29-quest.md)

**크기** 큼 · **착수 조건** P-25+P-31 (효과 어휘) · P-27 (`elite` 노드) · **P-30** (은혜 공급량)

**P-30이 앞에 서는 이유** `awardGrace`는 헌신 신이 정확히 하나일 때만 준다(`core/favor.ts:63`). P-30의 헌신 개입이 그 빈도를 바꾸므로, 공급량이 정해진 뒤에 45줄을 튜닝한다.

**실패 시 행동** 조합 하한 0.05(`npm test`)가 깨지면 **은혜 수치를 내린다.** 합성 게이트 완화(§4)를 되돌리지 않는다 — 그건 합성률 0.061을 고치는 유일한 수단이고, `enemyDamageScale`도 카드 풀도 아니다.

---

## 완료 정의

**은혜가 빌드를 만든다.** 같은 조합·같은 시드라도 고른 은혜에 따라 덱이 다르게 굴러가고, 조합 고유 보상이 실제로 나온다.

```bash
npm run validate                                   # 위반 0
npm run sim -- --runs 2000 --stratified
#   → 슬롯 5칸 중 평균 3칸 이상이 12층까지 채워진다
#   → 합성률이 0.061 → 0.25 이상
npm test                                           # 조합 하한 0.05 통과
npm run tune                                       # ⚠(|차이| ≤ 0.10) 늘지 않았는지 본다 — 보고만
```

하한이 깨지면 **은혜 수치를 내린다.** `enemyDamageScale`이나 카드 풀로 되돌리지 않는다.

## 지금 상태

`grace`는 있다. 하데스식이 아닐 뿐이다.

| | 지금 | 하데스 2 |
|---|---|---|
| 획득 | 헌신 단계 신이 정확히 하나일 때 전투 후 (`core/favor.ts:63`) | 방 보상 |
| 선택 | 마일스톤 2·6에서 **덱의 해당 신 카드 한 장** (`ui/choices.tsx:56`) | **3택1** |
| 적용 범위 | 카드 한 장 | **행동 슬롯** (그 슬롯의 모든 행동) |
| 효과 | 2: 강화 · 4: 오라 +1스택 · 6: 비용 −1 (`core/upgrade.ts`에 하드코딩) | 데이터 |
| 성장 | 없음 | 힘의 석류로 레벨업 |
| 조합 | 합성 카드 10장 — 두 신 호의 ≥70 **및** 사용 ≥2 (`core/fusion.ts:6`) | 듀오 보온 |

선택지가 "어느 카드에 붙일까" 하나뿐이라 결정이 아니라 절차다. 효과 셋이 코드에 박혀 있어 콘텐츠로 늘릴 수도 없다.

**합성률 0.061이다.** 조합 고유 콘텐츠 10장이 스무 런에 한 번 나온다 — 사실상 없는 것과 같고, 조합마다 다르게 느껴지지 않는 이유 중 하나다.

## 조사 — 하데스가 실제로 하는 것

| 요소 | 하데스 2 |
|---|---|
| **슬롯** | 공격·특수·주술·질주·마력 다섯. **슬롯당 보온 하나**, 올림포스 신만 채운다 |
| 제안 | 한 번에 **3택1**. 핵심 슬롯 보온이 우선, 그다음 등급순 |
| 등급 | 일반 → 희귀 → 서사 → 듀오 → 전설 (5단). 등급은 주로 **수치 배율** |
| 성장 | 힘의 석류로 개별 보온 레벨업. 핵심 슬롯을 교체해도 **석류는 새 보온으로 넘어간다** |
| 듀오 | 두 신 각각의 보온을 **이미 갖고 있어야** 후보에 뜬다 |
| 전설 | 한 신의 보온 3개가 전제 (카오스·헤르메스 제외) |
| 숨은 굴림 | 전제를 다 채워도 내부 확률을 통과해야 한다. 실패하면 금화 |
| 리롤 | 주사위로 다시. 단, 제안됐던 것 하나는 후보에서 빠진다 |

**핵심은 등급이 아니라 슬롯이다.** 깊이는 "얼마나 센 보온인가"가 아니라 "다섯 자리를 어느 신으로 채웠는가"에서 나온다. 그리고 듀오의 전제가 **누적 소유**라는 게 중요하다 — 문턱을 넘는 게 아니라 쌓이면 열린다.

우리 합성은 반대다. 호의 70 **그리고** 사용 2회라는 **경성 문턱**이고, 호의는 조우마다 −3으로 새기까지 한다(`favorDecayPerEncounter`). 열리기 어렵게 설계돼 있다.

## 설계

### 1 · 슬롯 = 카드 태그

`Card.tags`가 이미 있다(`core/rules.ts:5`) — `attack`·`defend`·`utility`·`multi`·`token`. 이 다섯이 슬롯이다.

은혜는 **한 장이 아니라 그 태그의 모든 카드**에 붙는다. 하데스의 「공격 보온이 카드 한 장이 아니라 공격 행동 전체를 바꾼다」와 같은 자리다.

```json
{
  "id": "grace_zeus_attack_chain",
  "patron": "zeus",
  "slot": "attack",
  "tier": 2,
  "text": "네 손끝에서 갈라진다.",
  "effects": [{ "op": "chain", "value": 2 }]
}
```

슬롯당 하나. 이미 찬 슬롯에 새 은혜를 고르면 교체하고 **tier는 유지한다** — 하데스의 석류 승계 규칙 그대로.

효과는 카드와 같은 `Effect` DSL이다(`core/rules.ts:17`). **두 번째 진실을 만들지 않는다.**

[P-31](31-powers.md)이 그 DSL에 `power` 태그와 `thorns`를 더한다(`doom`은 뺐다 — `bleed`가 이미 `shell`을 통과한다). 은혜를 뽑기 전에 어휘가 굳어야 한다 — 아니면 은혜를 두 번 만든다.

### 2 · tier — 한 숫자가 등급이자 레벨이다

`graceMilestones` 2·4·6이 tier다. **같은 id의 은혜를 tier마다 한 줄씩 둔다.**

```
grace_zeus_attack_chain  tier 2  →  chain 2
grace_zeus_attack_chain  tier 4  →  chain 3
grace_zeus_attack_chain  tier 6  →  chain 4
```

- 마일스톤 2에서는 tier 2짜리만 후보에 뜬다 — **등장 문턱**
- 이미 가진 은혜가 다시 나오면 다음 tier로 올라간다 — **성장**

두 뜻이 한 숫자에 얹혀도 모순이 없다. tier가 곧 그 은혜의 세기고, 세기가 곧 그것이 뜰 수 있는 시점이기 때문이다.

**하데스의 희귀도는 우리 tier와 같은 것이다** — 등급도 수치 배율이고 석류 레벨도 수치 배율이다. 하데스는 그 배율 다이얼을 둘 갖고 있고, 우리는 하나로 합쳤다. 없는 것을 안 넣는 게 아니라 **이미 있는 것을 겹쳐 넣지 않는 것**이다.

정말로 없는 건 **제안 시점의 무작위 크기**다 — 하데스는 같은 보온이 일반으로도 서사로도 뜬다. 그건 넣지 않는다. 6회차가 「승률 하락에 따른 압축이 섞여 있다」며 압축과 수렴을 아직 못 가르는 상태인데, 제안마다 크기가 흔들리면 그 구분이 더 멀어진다. **7회차에서 그 지표가 정해진 뒤에 다시 본다.**

### 3 · 3택1

`patron` + 빈 슬롯으로 거른 뒤 시드로 셋을 뽑는다. `rewardOffer`(`sim/engine.ts:55` 근처)가 이미 하는 일이라 뽑기 코드를 재사용한다.

리롤은 넣지 않는다 — 자원(주사위)이 없고, 자원을 만들면 그것도 다이얼이다.

**설계하는 것은 열다섯이다.** 신 5 × 슬롯 3(그 신의 카드가 실제로 몰려 있는 태그)이 전부고, tier 3단은 같은 줄의 수치만 다르므로 생성기가 뽑는다(`logs/generation/` 절차 그대로). 45는 산출물 줄 수지 설계 단위가 아니다 — 45로 읽으면 착수가 미뤄진다.

### 4 · 합성 게이트를 누적으로 재배선

`canFuse`(`core/fusion.ts:6`)를 하데스의 듀오 전제 모델로 바꾼다.

```ts
// 지금: 두 신 호의 ≥70 AND 사용 ≥2   → 합성률 0.061
// 바꿈: 두 신 각각 은혜 ≥1            → 쌓이면 열린다
```

호의는 조우마다 −3으로 새므로(`favorDecayPerEncounter`) 문턱형 게이트와 상성이 나쁘다. 은혜 보유 수는 새지 않는다. **하데스가 「보온을 갖고 있어야」로 잡은 이유가 이것이다.**

숨은 굴림은 넣지 않는다. 하데스는 확률이 실패하면 금화를 주지만 우리에겐 금화가 없다 — 실패가 그냥 아무것도 아닌 게 된다.

### 5 · 슬롯 하나뿐이다

`scope: "run"`(런 전역 효과)은 **넣지 않는다.** 적용 경로가 둘이면 EV 환산도 둘이고 게이트도 둘인데, 슬롯 5칸이 이미 결정 공간을 만든다. 런 전역이 정말 필요해지면 그건 `applyFavorStageEffects`(`core/favor.ts:50`)가 이미 하는 일이고 그때 붙인다.

카오스식(선불 저주 → 지속 축복)은 **P-29가 가져간다.** 요구를 「지금 대가, 나중 보상」으로 바꾸는 것이 그 항목의 뼈대라 여기서 겹쳐 만들지 않는다.

## 게이트

기대값 밴드는 `tools/value.ts`의 `expectedValue`를 그대로 쓴다.

- 은혜는 **덱의 해당 태그 카드 수 × 효과값**으로 환산한다. 카드 한 장 강화(`×1.5`)가 지금 주는 값이 기준선이다 — **먼저 재고** 그 위아래로 잡는다. 공격 태그가 덱의 절반이면 같은 효과가 두 배로 들어간다
- 토큰 범위는 `token_scope`가 이미 신별 허용 토큰을 잰다(`tools/validate.ts:130`) — 은혜에도 태운다. **제우스 은혜가 아테나 토큰을 걸 수 없다**
- 슬롯 커버리지 — **한 신·한 tier에 후보가 3개 이상**이어야 3택1이 선다. 슬롯 5칸이 매 tier마다 다 찰 필요는 없다. 신당 슬롯 3 × tier 3단 = 9줄, 다섯 신이면 45줄이고 **설계는 열다섯이다**

`FailureKey`는 `value_outlier`·`token_scope`를 재사용한다. 새 키를 만들지 않는다.

## 함정

- **은혜는 승률 승수다.** 카드 하나를 6→9로 만드는 게 아니라 덱 전체의 기울기를 바꾼다. 32,000런 전에 2000런으로 방향부터 본다
- **슬롯 환산이 밴드를 깨는 자리다.** 아테나 덱은 `defend` 태그가 몰려 있어 방어 슬롯 은혜 하나가 카드 열 장에 들어간다. P-22의 완화 비율 상한(0.30)이 카드 풀에만 걸려 있어 은혜를 못 잡는다 — 은혜 환산도 그 비율에 합산한다
- **`state.grace`가 두 뜻을 갖게 된다.** 지금 `grace[god]`은 마일스톤 도달 횟수고 `applyFavorStageEffects`(`core/favor.ts:53`)가 **`>= 4`면 개입 스택을 +1** 준다. 은혜 tier로 재해석하면 그 줄이 조용히 다른 조건이 된다 — P-30이 개입을 다섯으로 늘린 직후라 영향이 크다. **셋 중 하나를 골라 리뷰에 적는다:** 뜻을 유지하고 은혜는 별도 필드 / `>= 4`를 은혜 보유 수로 다시 정의 / 그 줄을 지운다
- **`Action`은 `grace`를 그대로 쓰고 `choice`만 은혜 id가 된다.** 새 타입을 만들지 않는다 — 옛 로그는 [P-27 §재생](27-map.md)이 `logs/human/v1/`로 아카이브했고 재생 호환은 요구하지 않는다. 옛 마일스톤 효과 셋(`core/upgrade.ts`의 강화·비용 감소, `favor.ts:53`의 오라 +1)도 남길 이유가 없어졌다
- **합성 게이트 완화는 승률을 올린다.** 0.061 → 0.25면 조합 카드가 네 배로 들어온다. 합성 카드 밴드(6~10)를 재조정할 각오를 하고, 조정하면 리뷰에 이전 값과 사유를 남긴다
- `ui/choices.tsx:56` `GraceScreen`은 `CardRow`를 쓴다. 은혜는 카드가 아니므로 `Choice` 3개로 바꾼다 — 컴포넌트는 이미 있다(`:22`). 슬롯이 이미 찼으면 **무엇을 밀어내는지** 화면에 보여야 한다
- 봇 정책이 은혜를 골라야 한다. `bot_policy_version` `v4` → 올린다
