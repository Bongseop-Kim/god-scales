```bash

npm run sim -- --runs 200 --scenario fused_deck
npm run play                        # 사람이 1런
npm run sim -- --replay logs/human/*.json
```

## 구현 노트

### CLI 플레이 모드가 여기 있는 이유는 순서 충돌이다

T-6 ⑤는 전역 파라미터 조정의 근거가 룰 봇 승률이 아니라 **사람 플레이테스트**라고 못 박는다. 그런데 전역 파라미터는 바로 다음 세션(P-13)에서 고정되고, UI는 P-17까지 없다. **사람이 놀 수단이 동결 전에 존재해야 한다.**

`sim/runner.ts`의 봇 자리에 표준 입력을 끼우면 된다. 전투 로그 가독성은 P-04에서 이미 만들었으므로 새로 만들 것은 입력 루프뿐이다.

부수 이득 둘 — **UI를 제거해도 게임이 완주 가능하다는 I-3의 직접 증명**이 되고, P-17의 반출 형식(`{seed, actions, replay_mode: "action_log"}`)을 UI보다 먼저 확정해 준다.

### 합성 조건

조우 승리 시점에 **두 신의 호의가 모두 70 이상**이고 **그 조우에서 각 신의 카드를 각각 2장 이상** 사용했으면, 그 조합의 합성 카드 1장이 즉시 덱에 들어온다. 전투 보상과 별개이며 **런당 1회만** 발생한다.

합성 카드는 코스트 2~3, 기대값 허용 범위 6.0~10.0(일반 카드는 4.0~8.0), `exhaust`가 붙지 않아 덱에 남는다. `favor(patron)`은 **두 신 중 낮은 쪽**을 가리킨다(T-3.1).

### 생성 주의

**조합별로 생성한다**(T-6 ②). 프롬프트가 두 신의 토큰 어휘를 동시에 노출하므로 컨텍스트가 넓어지고, **통과율이 단일 신 카드보다 낮게 나올 것을 예상한다.** `pass_rate`를 조합별(`by_pairing`)로 따로 기록한다.

**한쪽 어휘만 쓰는 합성 카드를 반송하는 것이 `fusion_scope` 필터의 핵심이다**(T-6 ③). LLM은 두 어휘를 주면 한쪽에 치우친 결과를 상당히 많이 만든다. 통과시키면 합성 카드가 그냥 강한 단일 신 카드가 된다.

### 봇 정책 추가

| 판단 | 정책 |
|---|---|
| 합성 시도 | 하지 않는다. 두 신이 우연히 70 이상이 되면 그 조우에서 양쪽 카드를 2장씩 쓰도록 순서만 조정 |

**고정된 단일 전략이 오히려 두 개의 측정을 만든다**(T-6). `fusion_rate`가 룰 봇에서 0에 가깝고 LLM 에이전트에서 유의하게 높으면, 그것이 "판단할 수 있는 주체에게만 열리는 경로가 실재한다"는 직접 증거다.
