**이 문서의 용도**
사람이 미리 구해두거나 만들어두어야 하는 것을 정의한다. 코드로 만드는 것은 05에 있다. 이 문서에는 코드로 만들 수 없는 것 — 계정, 예산, 라이선스, 사람, 시간 — 과, 만들긴 하되 세션 안에서 즉흥으로 정하면 안 되는 것만 둔다.

## A-0. 결론

**에셋은 쓴다. 다만 만드는 것과 받아오는 것을 구분한다.**

| 종류 | 출처 | 언제 |
|---|---|---|
| 아이콘 (토큰·신·노드·자원) | [game-icons.net](https://game-icons.net/) · CC BY 3.0 · SVG | P-18 |
| UI 프레임·버튼·바 | [Kenney Interface](https://kenney.nl/assets/tag:interface) · CC0 | P-18 |
| UI 연출 | 코드 (CSS + Motion) | P-18 |
| **카드 일러스트** ~70장 | **직접 제작** | **콘텐츠 동결 후 (P-21)** |
| **스프라이트 시트 이펙트** | **직접 제작** | **콘텐츠 동결 후 (P-21)** |
| **사운드** ~10종 | **직접 제작 또는 수급** | **콘텐츠 동결 후 (P-21)** |

**직접 제작하는 셋은 전부 콘텐츠 동결 후다.** 카드는 회차마다 폐기·재생성되고 id가 바뀌므로(T-6 ⑤), 동결 전에 만들면 존재하지 않을 카드의 그림과 소리를 만들게 된다. 근거는 A-2.4에 있다.

**P-18은 자리를 만들고 P-21은 채운다.** P-18의 완료 정의가 "에셋이 없어도 안 깨진다"이고, P-21의 완료 정의가 "넣으면 동작한다"인 이유가 이것이다.

**LLM으로 일러스트를 생성하지 않는다**(B-3). 그 항목이 백로그에 있는 이유는 생성 비용과 실패율이었고, 직접 그리면 그 이유가 사라진다. 다만 **생성 파이프라인이 아니라 사람의 작업**이므로 논지에는 기여하지 않는다 — 게임이 좋아 보이는 것과 파이프라인이 증명되는 것은 별개다.

**미리 준비해야 하는 것은 넷이다.**

| | 무엇 | 언제까지 |
|---|---|---|
| 1 | 사람 플레이테스트 인원 | 동결 게이트(P-13) 전 |
| 2 | 배포 대상 계정 | P-19 시작 전 |
| 3 | 폰트 결정 | P-17 시작 전 |
| 4 | 에셋 다운로드 + 라이선스 파일 | P-18 시작 전 (A-3) |

**API 키와 예산은 준비물이 아니다.** 생성과 에이전트 판단은 전부 구독 토큰으로 돌린다(A-6).

**카드 일러스트는 마지막에 그린다.** 이유는 A-2.4에 있고, 그 한 문단이 이 문서에서 가장 실질적인 절약이다.

### A-2.1 토큰 배지 9종 — 아이콘 + 글자

**아이콘과 한 글자를 함께 쓴다.** 아이콘만 쓰면 9종을 한 화면에서 구분하는 데 학습이 필요하고, 글자만 쓰면 눈에 걸리지 않는다. 배지는 `아이콘 배경 + 한 글자 오버레이 + 스택 수`이며, 아이콘이 형태를 주고 글자가 즉시 읽히게 한다.

game-icons.net 검색어는 아래를 출발점으로 하되 직접 골라서 확정한다 — 정확한 이름은 사이트에서 확인한다.

| 토큰 | 글자 | 색 | 검색어 |
|---|---|---|---|
| `shock` | 감 | 제우스 | lightning · electric |
| `displace` | 지 | 포세이돈 | hourglass · time · slow |
| `soaked` | 침 | 포세이돈 | water drop · splash |
| `bulwark` | 벽 | 아테나 | shield · rampart |
| `deflect` | 반 | 아테나 | mirror · reflect · bounce |
| `bleed` | 혈 | 아레스 | bleeding wound · blood |
| `frenzy` | 광 | 아레스 | rage · berserk |
| `mark` | 표 | 아르테미스 | target · crosshair |
| `crit` | 치 | 아르테미스 | bullseye · critical |

`chain`은 토큰이 아니라 연산자이므로(R-4.1) 배지가 없다 — 파급은 상태가 아니라 그 순간의 효과이며, 연출(A-2.5)과 로그로만 나타난다.

**아이콘은 SVG로 인라인한다.** 9종 × 1KB 남짓이므로 번들에 넣는 편이 요청 9개보다 싸고, `currentColor`로 신 색을 그대로 받는다.

### A-2.3 카드 컴포넌트와 일러스트 규약

카드 한 장의 구조 — **일러스트 자리를 처음부터 비워두고 placeholder로 채운다.**

```
┌─────────────────┐
│ [코스트]   [태그] │
│                 │
│   ← 일러스트 →   │   art/cards/{card_id}.webp
│                 │   없으면 placeholder
│─────────────────│
│ 카드 이름        │
│ 효과문           │
└─────────────────┘
테두리 = 귀속 신의 색 (합성 카드는 두 색 그라디언트)
```

**카드 스키마를 건드리지 않는다.** `art` 필드를 추가하지 않고 **`art/cards/{card_id}.webp` 파일 규약**으로 연결한다.

이유가 셋이다. 스키마가 그대로이므로 검증 게이트(T-6)를 손대지 않아도 되고, LLM이 존재하지 않는 경로를 생성할 여지가 없으며, 파일을 넣는 것만으로 교체가 끝난다. **일러스트 교체는 코드 변경이 아니라 파일 드롭이다.**

placeholder는 신 색 그라디언트 + 신 아이콘 워터마크. 파일이 아니라 CSS이므로 70장을 미리 만들 필요가 없다.

### A-2.4 일러스트는 콘텐츠 동결 후에 그린다

**이것이 이 문서에서 가장 실질적인 절약이다.**

카드는 회차마다 자동 조정되고 3회 조정 후에도 임계값을 벗어나면 **폐기되어 재생성된다**(T-6 ⑤). 카드 id도 함께 바뀐다. 회차가 끝나기 전에 그리면 **그린 그림의 일부가 존재하지 않는 카드의 것이 된다.**

| 시점 | 상태 |
|---|---|
| P-06 ~ P-15 | 카드 id가 계속 바뀐다. **그리지 않는다** |
| P-18 | placeholder로 화면을 완성한다 |
| **P-20 이후 (콘텐츠 동결)** | **id가 확정된다. 여기서 그린다** |

동결 후 `data/cards.json`에서 id·이름·효과문을 뽑아 작업 목록을 만든다.

```bash
npm run art -- --list   # id, 이름, 귀속 신, 효과문 → 작업 목록 CSV
npm run art -- --check  # art/cards/ 에 없는 id 나열
```

**시연이 급하면 우선순위가 있다.** 시작 덱 카드(신별 4장 × 5신 = 20장)와 합성 카드 10장이 화면에 가장 자주 뜬다. 30장이면 체감의 대부분이 덮인다.

### A-2.5 신 색 5종

CSS 변수 5줄. 신화적 연상과 화면상 구분을 동시에 만족해야 한다.

```css
--zeus:      #D4A017;  /* 뇌전 — 황금 */
--poseidon:  #2E7D8F;  /* 심해 — 청록 */
--athena:    #7A8B5C;  /* 올리브 — 회녹 */
--ares:      #9B2226;  /* 피 — 진홍 */
--artemis:   #8E7CA6;  /* 달 — 은보라 */
```

**이 값은 가정치다.** 어두운 배경 기준으로 골랐고 실측이 없다. 검증 기준은 하나 — 전투 화면에서 두 신의 카드가 손패에 섞여 있을 때 구분되는가. 구분되지 않으면 명도를 벌린다.

라이벌 쌍(제우스↔포세이돈, 아테나↔아레스)이 색상환에서 서로 멀리 있는 것은 의도다. 라이벌 관계가 화면에서 읽히면 R-4의 구조를 설명할 필요가 줄어든다.

### A-2.6 전투 연출

**연출은 반복 빈도에 반비례해서 넣는다.** 이것이 이 절의 유일한 규칙이다.

| 사건 | 런당 빈도 | 연출 | 목적 |
|---|---|---|---|
| 카드 사용 | ~100 | **최소** — press `scale(0.97)` 120ms, 손패에서 제거 | 피드백 |
| 피해·회복 숫자 | ~200 | 대상 위에 팝, 400ms 후 소멸 | **설명 — 어느 적에게 들어갔는가** |
| 토큰 부여 | ~80 | 배지 펄스 1회 160ms | 상태 표시 |
| HP·호의 바 변동 | ~150 | `scaleX` 트윈 200ms | 급격한 변화 방지 + 크기 전달 |
| `chain` 파급 | ~20 | 대상마다 60ms stagger | **설명 — 파급이 몇 체에 갔는가** |
| 조우 전환 | ~10 | 페이드 200ms | 공간적 일관성 |
| 요구 제시 | ~7 | 배너 슬라이드인 250ms | 상태 표시 |
| 역린 개입 | 0~5 | 화면 가장자리 신 색 플래시 | 상태 표시 |
| 은총 마일스톤 | 0~3 | 토스트 + 대상 카드 강조 | 설명 |
| **합성 카드 획득** | **0~1** | **가장 크게** — 두 신 색이 합쳐지는 카드 등장 | delight |

**카드 사용이 런당 100회라는 것이 설계의 출발점이다.** 100회 반복되는 동작에 화려한 연출을 붙이면 3분 만에 거슬리기 시작하고 시연에서 지루해진다. 반대로 합성 카드 획득은 런당 최대 1회이므로 크게 써도 된다 — **거기가 이 게임의 절정이고**(R-3.5), 심사자가 기억할 장면이다.

**`chain` 파급의 stagger는 장식이 아니다.** 파급은 이 게임의 특징적 메커니즘인데(R-4.1) 숫자가 동시에 뜨면 광역 카드와 구분되지 않는다. 60ms씩 어긋나면 "타고 흐른다"가 보인다.

**연출은 두 범주이고 예산이 다르다**

| 범주 | 예산 | 수단 | 무엇 |
|---|---|---|---|
| **UI 피드백** (고빈도) | **300ms 미만** | CSS transition · Motion | 카드 press, 피해 숫자, 배지 펄스, 바 트윈, 화면 전환 |
| **극적 연출** (저빈도) | 480ms+ 허용 | **스프라이트 시트** | 역린 개입, 합성 획득, 보스 등장 |

**스프라이트가 300ms 규칙에서 면제되는 대가로 저빈도 연출에만 쓴다.** 12프레임을 300ms 안에 넣으면 25fps로 끊기고, 12프레임에 필요한 480ms는 UI 피드백의 예산이 아니다. **카드 사용(런당 100회)에 스프라이트를 붙이면 3분 만에 거슬린다.**

**규격**

```css
--ease-out:    cubic-bezier(0.23, 1, 0.32, 1);      /* 등장·소멸 */
--ease-in-out: cubic-bezier(0.77, 0, 0.175, 1);     /* 화면 내 이동 */
```

- **`ease-in`은 쓰지 않는다.** 첫 순간을 지연시켜 굼뜨게 느껴진다
- **`transform`과 `opacity`만 애니메이션한다.** HP 바는 `width`가 아니라 `scaleX` — `width`는 레이아웃을 유발한다
- 빠르게 반복 트리거되는 것(토큰 배지, 바)은 keyframes가 아니라 transition — 중간에 끊고 새 목표로 갈 수 있다

| GSAP | 불채택 | 타임라인이 필요한 곳이 2군데뿐 |
| canvas-confetti | 불채택 | 톤 불일치 + 스프라이트가 그 자리를 덮는다 |
| 스프라이트 재생 라이브러리 | 불채택 | CSS `steps()`로 끝난다 |

**Motion을 넣는 유일한 이유는 exit 애니메이션이다.** CSS는 DOM에서 제거되는 요소를 애니메이션할 수 없고 React는 즉시 언마운트한다. 언마운트 지연을 손으로 관리하면 **"화면에는 있지만 게임 상태에는 없는 요소"를 UI가 추적하게 되고, 그것이 정확히 I-3이 경계하는 상태다.** 화면 전환 crossfade · 손패 카드 퇴장 · 토스트 · 배너에서 반복되므로 라이브러리가 값을 한다.

**GSAP을 빼는 근거** — 타임라인이 진짜 필요한 것은 합성 카드 획득과 역린 개입 둘뿐이고, WAAPI로 `await el.animate(...).finished`를 순차 실행하면 15줄이다. 그것 때문에 두 번째 애니메이션 패러다임을 들이면 **어느 시스템이 이 요소를 잡고 있는지 알 수 없는 상태**가 생긴다.

**confetti를 빼는 근거** — 이 게임은 부채와 신의 노여움에 관한 어두운 게임이고 컨페티는 축하다. 합성 카드의 절정은 축하가 아니라 **두 신의 색이 합쳐지는 융합**이며, 그것은 스프라이트 시트의 몫이다.

**Motion 사용 시 주의** — 단축 prop(`x`/`y`/`scale`)은 메인 스레드 rAF이므로 하드웨어 가속이 아니다. 이 게임의 동시 애니메이션은 최대 10개 남짓(chain 3체 × 숫자·배지·바)이라 실무상 문제되지 않지만, 부하가 보이면 full transform 문자열로 바꾼다.

### A-2.8 스프라이트 시트

**`background-position`이 아니라 `transform`으로 넘긴다.** `background-position`은 paint를 유발해 GPU 가속되지 않으며, 이는 위 규격의 "`transform`과 `opacity`만"과 같은 이유다.

```css
/* ❌ paint 유발 */
@keyframes sprite { to { background-position: -3072px 0 } }

/* ✅ GPU */
.fx       { overflow: hidden; width: 256px; height: 256px }
.fx > img { animation: sprite 480ms steps(12) forwards }
@keyframes sprite { to { transform: translateX(-3072px) } }
```

- **처음부터 2x로 만들고 CSS에서 반으로 줄인다.** 레티나 시트를 두 벌 관리하지 않는다
- 12프레임 × 256px = 3072px 폭이면 모바일 텍스처 한계에 근접한다. 세로로 감거나 시트를 나눈다
- 개별 이미지 시퀀스가 아니라 시트 하나 — 요청 1개, 디코드 1회
- 프레임 수는 12 안팎이면 충분하다. 손그림 애니메이션이 12fps로 도는 것과 같은 이유다

### A-2.9 사운드

**Web Audio 30줄로 시작한다.** 버퍼를 한 번 디코드하고 재생마다 `AudioBufferSourceNode`를 만들면 겹침 재생이 정확히 해결된다 — 라이브러리가 하는 일이 그것이다. 모바일 autoplay 해제는 첫 `pointerdown`에서 `ctx.resume()` 3줄. **엣지 케이스가 없어서 직접 소유해도 나중에 물리지 않는다.** 부족하다고 판명되면 그때 Howler를 넣는다.

**빈도 규칙이 소리에는 더 가혹하다.**

| 사건 | 런당 | 소리 |
|---|---|---|
| 카드 사용 | ~100 | **아주 짧고 미묘하게.** 여기서 실패하면 3분 만에 끄고 싶어진다 |
| 피격 · 회복 | ~200 | 짧게. 피해량에 따라 피치를 살짝 |
| 토큰 부여 | ~80 | 거의 들리지 않을 정도 |
| 역린 개입 | 0~5 | 크게 |
| 합성 획득 | 0~1 | **가장 크게** |
| 승 · 패 | 1 | 런의 마침표 |

**음소거 스위치는 필수다.** 시연장에서 소리를 못 켤 수도, 켰다가 문제가 될 수도 있다. `prefers-reduced-motion`과 같은 등급의 기본 장치이며 기본값은 켜짐으로 두되 첫 화면에서 끌 수 있어야 한다.

**연출이 플레이를 막지 않는다.** 애니메이션 중에도 입력을 받고, 다음 입력이 오면 진행 중인 연출을 즉시 완료시킨다. 시연에서 연출 때문에 기다리는 것이 최악이고, 빠르게 두는 플레이어가 답답해지면 안 된다.

**`prefers-reduced-motion: reduce`에서 이동 모션만 제거하고 opacity와 색 전환은 남긴다.** 접근성 기본이자 시연 안전장치다 — 연출이 문제되면 이 경로로 끌 수 있다.

### A-2.7 favicon

이모지 하나를 SVG로 감싼 data URI. 파일 없음.

```html
<link rel="icon" href="data:image/svg+xml,<svg xmlns='http://www.w3.org/2000/svg' viewBox='0 0 32 32'><text y='26' font-size='28'>⚖️</text></svg>">
```

## A-3. 에셋 다운로드와 라이선스

**P-18 시작 전에 받아두고 라이선스 파일을 만든다.** 세션 안에서 에셋을 고르기 시작하면 그 세션이 에셋 쇼핑으로 채워진다.

### A-3.1 받을 것

| 출처 | 라이선스 | 받을 것 | 형식 |
|---|---|---|---|
| [game-icons.net](https://game-icons.net/) | **CC BY 3.0 — 귀속 필수** | 토큰 9 · 신 5 · 노드 3 · 자원 4 = **21종** | SVG |
| [Kenney Interface](https://kenney.nl/assets/tag:interface) | **CC0 — 귀속 불필요** | 패널 · 버튼 상태 · 바 프레임 · 포커스 링 | PNG 또는 SVG |

game-icons.net은 아이콘마다 **제작자가 다르다.** 다운로드 시 제작자 이름이 파일명이나 페이지에 있으므로, **받는 그 자리에서 기록한다.** 21개를 다 받은 뒤에 되짚으면 어느 것이 누구 것인지 찾아야 한다.

```
art/icons/{용도}-{제작자}.svg      예: token-shock-lorc.svg
```

파일명에 제작자를 넣으면 귀속 파일을 스크립트로 생성할 수 있고, 나중에 아이콘을 교체해도 귀속이 따라온다.

### A-3.2 `ATTRIBUTION.md`

**CC BY는 귀속이 라이선스 조건이다.** 빠뜨리면 라이선스 위반이고, 심사 제출물에서 이것이 없으면 그 자체가 감점 요인이다.

```markdown
# 사용한 자산

## 아이콘 — game-icons.net (CC BY 3.0)
| 용도 | 아이콘 | 제작자 |
|---|---|---|
| shock 토큰 | Lightning Arc | Lorc |
| ... | ... | ... |

## UI — Kenney (CC0)
Kenney Interface Pack — https://kenney.nl/assets/tag:interface
CC0이므로 귀속 의무는 없으나 명시한다.

## 카드 일러스트
직접 제작. 이 저장소의 라이선스를 따른다.

## 폰트
(A-1.2의 선택에 따라)
```

배포본에서도 접근 가능해야 하므로 `ui/`에 크레딧 화면을 두거나 `dist/ATTRIBUTION.md`로 함께 배포한다.

### A-3.3 그래도 만들지 않는 것

| 항목 | 왜 | 대체 |
|---|---|---|
| 배경 음악 | 루프 하나가 시연 내내 도는 것은 SFX보다 빨리 거슬린다. SFX가 먼저다 | 없음 |
| 적 스프라이트 | 적의 정보는 HP와 의도이며 둘 다 숫자다. 12종을 그리는 시간이면 카드 12장을 그리는 편이 체감에 크게 기여한다 | 이름 + 아이콘 + HP 바 + 의도 |
| 구역 배경 | 정보를 담지 않는다 | CSS 그라디언트 두 종 |
| 로고 | 제목 텍스트로 충분하다 | `<h1>` |
| **LLM 일러스트 생성** | 직접 그리므로 필요가 없어졌다. 생성 파이프라인으로서의 가치는 B-3에 남아 있다 | 직접 제작 |

**적 스프라이트를 뺀 근거가 이 표에서 유일하게 논쟁적이다.** 그릴 여력이 남으면 보스 2종부터 그린다 — 구역당 1회씩 등장하고 그 조우가 가장 길다.

## A-4. 사람 자원 — 플레이테스트

**이것이 이 문서에서 가장 미리 준비해야 하는 항목이다.** 돈으로 살 수 없고, 필요할 때 즉석에서 구할 수 없다.

| 항목 | 값 |
|---|---|
| 인원 | 3~5명 |
| 1인당 | 2런 × 10~15분 = 약 30분 |
| 총 런 수 | 6~10 |
| 필요 시점 | **동결 게이트(P-13) 전** 1회, P-18 이후 1회 |

**왜 미리 섭외해야 하는가.** T-6 ⑤는 조정 순서 3번(HP 예산·호의 변동량 같은 전역 파라미터)의 근거가 룰 봇 승률이 아니라 **사람 플레이테스트**라고 못 박는다. 그런데 전역 파라미터는 동결 게이트에서 고정되고, 그 이후 바꾸면 이전 회차 데이터가 전부 무효가 된다. **따라서 사람 런은 동결 게이트 이전에 확보되어야 한다.**

**UI는 그때 아직 없다.** UI 세션(P-17)은 동결 게이트보다 한참 뒤다. 그래서 동결 직전에 **CLI 플레이 모드**를 만든다 — `npm run play`가 전투 로그를 출력하고 숫자 입력으로 카드와 대상을 고르는 20~30줄짜리 루프다. `sim/runner.ts`의 봇 자리에 사람 입력을 끼우면 끝난다.

CLI 플레이 모드에는 부수 이득이 둘 있다. UI를 제거해도 게임이 완주 가능하다는 I-3의 직접 증명이 되고, P-17의 반출 형식(`{seed, actions}`)을 UI보다 먼저 확정해 준다.

**사람 런도 계측에 남긴다**(T-9.3). 통계가 되지 않는 런 수지만, 기록하지 않으면 난이도 조정의 근거가 문서에 존재하지 않게 되고 "루프가 콘텐츠를 수렴시켰다"는 서술에 사람의 개입이 숨는다.

## A-6. 생성 수단 — 구독 토큰

**API 키를 쓰지 않는다.** 콘텐츠 생성(P-06, P-08, P-11, P-12)과 에이전트 판단(P-16)은 전부 Claude Code 세션에서 나온다. 예산은 준비물이 아니고, 대신 **사용량 한도가 제약이 된다.**

### A-6.1 파이프라인은 그대로 성립한다

**논지의 경계는 API 호출이 아니라 사람의 개입 지점이다.** I-5는 "사람이 직접 카드를 작성해 `data/`에 넣지 않는다. 사람의 개입은 스키마·임계값·프롬프트 수정으로만 이루어진다"고 정의한다. 생성이 스크립트에서 나오든 Claude Code 세션에서 나오든 이 경계는 같은 자리에 있다.

| | API 키 | 구독 토큰 |
|---|---|---|
| 사람이 쓰는 것 | 스키마 · 임계값 · 프롬프트 | 동일 |
| 카드를 쓰는 것 | `tools/generate.ts` | Claude Code 세션 |
| 게이트 | `tools/validate.ts` | 동일 |
| 반송 경로 | 자동 재호출 | 반송 결과를 세션에 다시 넣는다 |
| 증거 | API 로그 | **생성 세션 트랜스크립트** |

**반송 경로가 자동이 아닌 것은 논지의 손실이 아니라 서술의 정확도 문제다.** 리포트에 "루프가 자동으로 돌았다"고 쓸 수 없고 "게이트가 반송하면 같은 프롬프트로 재생성했다"고 써야 한다. 후자가 실제로 일어난 일이고, T-9.3이 요구하는 정직성이 바로 그것이다.

**생성 세션 트랜스크립트를 `logs/generation/`에 저장한다.** 이것이 API 로그를 대체하며, 오히려 더 강한 증거다 — 무엇을 요청했고 무엇이 돌아왔는지가 그대로 보인다. `prompt_version`과 함께 커밋한다.

### A-6.2 무엇이 실제로 바뀌는가

| | 영향 |
|---|---|
| **구조화 출력이 없다** | `output_config.format`은 API 기능이다. 세션 출력은 형식이 강제되지 않으므로 **`dsl_parse` 반송률이 올라갈 것을 예상한다.** ajv 게이트가 더 중요해진다 |
| **프롬프트 캐싱을 제어할 수 없다** | 조립 순서를 신경 쓸 필요가 없어졌다. 그만큼 P-06이 단순해진다 |
| **`effort` · `thinking`을 지정할 수 없다** | 세션 설정을 따른다. 에이전트 판단의 일관성을 위해 **한 회차는 한 세션 안에서 끝낸다** |
| **`usage` 계측이 없다** | 토큰 계측은 리포트에서 빠진다. 대신 **세션 수와 소요 시간**을 기록한다 |
| **처리량이 한도에 묶인다** | 이것이 유일한 실질 제약이다. A-6.3 참조 |

### A-6.3 한도가 예산을 대체한다

**콘텐츠 생성은 문제되지 않는다.** 1회차 전체가 카드 45 · 합성 50 · 적 20 · 요구 16 = 약 130회 요청이고, 배치로 묶여 있어 세션 몇 번이면 끝난다. 3회차라도 재생성은 반송분만이므로 총 300회 안쪽이다.

**문제는 에이전트다.** 원래 설계는 20런 × 런당 ~100 판단 = 2,000회였다. 구독으로 이 규모는 성립하지 않는다.

**대응은 모델을 낮추는 것이 아니라 판단 지점을 줄이는 것이다.** 상세 설계는 P-16에 있고, 요지는 이렇다 — 전투 내 카드 순서와 대상 선택은 룰 봇에게 맡기고, 에이전트는 **전략 층만 판단한다**(신 선택 · 조우 전략 · 상충 요구 · 층 경로 · 휴식 · 보상 · 마일스톤). 런당 판단이 ~100에서 ~30으로 줄고, 10런이면 300회다.

**그리고 이 축소가 측정을 개선한다.** T-6이 에이전트에게 묻는 질문은 "판단이 필요한 상태에 도달할 수 있는가, 선택이 선택인가"이지 "카드를 잘 쓰는가"가 아니다. `fusion_rate` 격차는 전략 판단에서 나오지 전투 조작에서 나오지 않는다. **전투를 룰 봇에 맡기면 두 주체의 차이가 전략 층에만 남아 격차의 원인이 오히려 깨끗하게 분리된다.**

**T-6이 요구하는 "수십 런"의 하단이 10이다.** 부족한 부분은 시나리오 주입으로 보완한다 — 그것이 T-6이 애초에 시나리오 시뮬을 둔 이유다.

### A-6.4 헤드리스 옵션

Claude Code에는 비대화형 실행 모드가 있다. 이것이 구독 인증으로 동작하고 사용량 한도 안에 들어온다면, `tools/generate.ts`가 이를 호출해 반송 루프를 자동화할 수 있다.

**다만 계획을 여기 걸지 않는다.** 구독 한도는 대화형 사용을 전제로 설계되어 있고, 수백 회 스크립트 호출이 그 범위에 든다고 단정할 수 없다. **먼저 소규모로 확인하고**, 되면 P-06의 반송 루프를 자동화해 세션 왕복을 줄인다. 안 되거나 애매하면 A-6.1의 반수동 경로가 기본이며, 그 경로만으로도 이 프로젝트는 성립한다.

### A-6.5 API로 전환해야 할 때

아래 중 하나라도 해당하면 API 키를 발급하는 편이 낫다. 그때의 비용은 총 $45 안팎이다(생성 $14 + 에이전트 $31).

- 에이전트 런을 20 이상으로 늘려야 한다
- 회차를 5회 이상 돌려야 한다
- 반송 루프의 세션 왕복이 회차 수를 제약하는 것이 관측된다 (B-3의 "생성 비용 최적화" 착수 조건과 같은 신호다)

**지금은 해당하지 않는다.** 구독으로 시작하고, 위 셋 중 하나가 실제로 관측되면 그때 전환한다.

## A-7. 준비물 추가 규칙

- 코드로 만들 수 있으면 준비물이 아니다. 05의 세션 안으로 들어간다
- 없어도 게임이 성립하면 준비물이 아니다. A-3에 적고 넘어간다
- 시간이 필요한 것(사람 섭외, 계정 발급, 라이선스 확인)만 여기 남는다
