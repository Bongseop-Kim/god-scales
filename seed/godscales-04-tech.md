## T-1. 스택

**웹 / TypeScript.** 선택 근거는 개발 속도와 `core/`의 헤드리스 실행 용이성이다.

| 항목 | 결정 |
|---|---|
| 언어 | TypeScript (strict) |
| 런타임 | 브라우저 + Node (동일 `core/` 공유) |
| 빌드 | Vite |
| UI | React |
| 시뮬 실행 | Node CLI — `npm run sim` |
| 파이프라인 실행 | Node CLI — `npm run generate` / `validate` / `tune` |
| 배포 | 정적 호스팅. URL 하나로 즉시 플레이 |
| 검증 | JSON Schema (ajv) |

**배포본은 API 키 없이 실행된다.** LLM 호출은 `tools/` 아래 빌드타임 경로에만 존재하고, 빌드 산출물에는 포함되지 않는다. 이것이 정적 호스팅이 성립하는 조건이며, `core/`의 네트워크 접근 금지(I-1)와 함께 확인된다.

### T-1.1 클라이언트 저장소를 쓰지 않는다

**localStorage · IndexedDB · 쿠키를 어느 것도 사용하지 않는다.** 브라우저에 남길 상태가 없기 때문이다 — 세이브/로드와 설정 화면은 범위 밖이고(S-3), 메타 프로그레션은 기각되어 있으며(B-6), 은총·업그레이드·합성 카드는 런 종료 시 소멸한다(R-11). 서버가 없다는 것은 저장소를 클라이언트로 옮겨야 한다는 뜻이 아니라 저장할 것이 애초에 없다는 뜻이다.

쿠키는 특히 해당 사항이 없다. 서버로 전송되는 것이 존재 이유인데 전송할 서버가 없다.

**필요한 것은 저장이 아니라 반출이다.** T-9.3이 사람 플레이테스트 런을 계측에 남기라고 요구하는데, 브라우저에서 돈 런이 파이프라인에 도달하는 경로가 있어야 한다. I-2에 의해 `seed + action[]`이면 런이 완전 복원되므로 파일 하나로 끝난다.

```
런 종료 화면 → { seed, actions, replay_mode: "action_log" } JSON 다운로드
             → logs/human/ 에 넣는다
             → npm run sim --replay logs/human/*.json 이 집계에 합친다
```

`ui/`는 상태를 읽어 직렬화할 뿐이므로 I-3을 위반하지 않는다. 진행 중인 런을 새로고침 후에도 유지하는 것은 세이브/로드이며 범위 밖이다. 시연 안정성 때문에 필요해지면 그때 B-5에서 꺼낸다.

**단일 언어로 `core/`를 브라우저와 Node가 공유하는 것이 이 스택의 핵심 이득이다.** 게임 코드와 시뮬 코드가 같은 로직을 쓰므로, 시뮬 결과가 실제 플레이와 어긋날 여지가 없다. 엔진을 쓰면 이 보장을 별도로 만들어야 한다.

게임 엔진을 쓰지 않는다. 물리·씬 그래프·에셋 파이프라인이 필요 없고, 엔진의 런루프가 `core/`의 순수성(I-1)을 침식한다.

## T-2. 디렉터리

```
core/            순수 로직 — 외부 의존 없음
  state.ts       상태 타입 (덱, 전투, 호의, 맵 진행)
  reducer.ts     (state, action) → state
  rng.ts         시드 기반 PRNG
  rules.ts       효과 DSL 해석
  favor.ts       호의 상수(초기값·단계 경계·감쇠·방치·요구 보상과 페널티),
                 판정, 단계별 전역 효과, 역린 개입, 은총 마일스톤
  fusion.ts      합성 조건 판정, 합성 카드 획득
  upgrade.ts     카드 업그레이드 균일 규칙
  targeting.ts   대상 해석 (self / enemy / all_enemies)
  demands.ts     요구 제시·판정, 상충 판정
  combat.ts      턴 진행, block 소멸, 더미 순환
  map.ts         구역·층 구조 상수, 노드 진행
data/            게이트를 통과한 콘텐츠
  cards.json  enemies.json  gods.json  demands.json
sim/             헤드리스 실행 — core만 참조
  runner.ts      1런 실행 → 로그
  bots/rule.ts   룰 기반 봇
  bots/llm.ts    LLM 에이전트
  scenarios.ts   시작 상태 오버라이드
  replay.ts      action 로그 재생 — 사람 플레이테스트 런 집계용 (T-1.1)
  report.ts      집계 (조합 행렬 포함)
logs/            런 로그 — human/ 은 브라우저에서 반출한 사람 런
tools/           빌드타임 파이프라인 — 빌드 산출물에 포함되지 않는다
  generate.ts  validate.ts  tune.ts
prompts/         버전 관리되는 프롬프트
ui/              표현 층 — 읽기 전용
```

의존 방향은 단방향이다. `core/`는 아무것도 import하지 않는다. `core/`가 `sim/`이나 `ui/`를 참조하는 순간 I-1이 깨진다.

**맵은 데이터 파일이 아니라 `core/map.ts`의 상수다.** 구역 2개 × 6층 구조가 고정이고 노드 종류가 셋뿐이므로(R-8), 생성 대상으로 둘 이유가 없다. 맵을 생성하면 검증 게이트가 관리할 콘텐츠가 하나 늘고 통과율 지표만 복잡해진다.

`core/targeting.ts`를 분리한 이유는 대상 해석이 효과 적용과 섞이면 `all_enemies` 처리와 `chain` 파급이 같은 코드에 뭉치기 때문이다. 대상 집합을 먼저 확정하고 효과를 적용한다.

## T-3. 데이터 모델

### T-3.1 카드 스키마

```json
{
  "id": "card_zeus_chain_bolt",
  "name": "연쇄 벼락",
  "patron": "zeus",
  "cost": 1,
  "target": "enemy",
  "effects": [
    { "op": "damage", "value": 6 },
    { "op": "apply_token", "token": "shock", "stacks": 1 },
    { "op": "chain", "value": 3, "when": "favor(patron) >= 70" },
    { "op": "self_damage", "value": 2, "when": "favor(patron) < 30" }
  ],
  "tags": ["attack", "multi"]
}
```

**합성 카드는 신 하나가 아니라 조합에 귀속된다**(R-3.5).

```json
{
  "id": "card_fused_zeus_poseidon_deluge",
  "name": "범람하는 뇌우",
  "patron_pair": ["poseidon", "zeus"],
  "cost": 2,
  "target": "enemy",
  "effects": [
    { "op": "apply_token", "token": "soaked", "stacks": 1 },
    { "op": "damage", "value": 5 },
    { "op": "chain", "value": 4, "when": "has_token(target, soaked) >= 1" }
  ],
  "tags": ["attack", "fused", "multi"]
}
```

`chain`은 주 대상을 기준으로 파급하므로 `target: enemy` 카드에만 쓸 수 있다(T-4). 이 카드가 `multi` 태그를 갖는 것은 `chain`이 만드는 파급 때문이지 `target` 때문이 아니다.

`patron`과 `patron_pair` 중 **정확히 하나**를 갖는다. 스키마는 `oneOf`로 이를 강제한다. 귀속 없는 카드는 존재하지 않는다(I-4).

`patron_pair`는 신 id를 사전순으로 정렬해 적는다. 정렬하지 않으면 같은 조합이 두 표기를 갖고 집계가 쪼개진다.

**조합 귀속이 측정을 깨지 않는 이유는 층화 시뮬의 단위와 일치하기 때문이다.** 합성 카드는 정의상 5×5 행렬의 한 칸에서만 등장하므로, 조합 내에서 델타를 계산하고 조합 간 평균을 내는 규칙(T-7)이 그대로 성립한다. 오히려 단일 신 카드보다 교락이 적다.

`patron`은 일반 카드의 필수 필드다. `favor(patron)` 조건이 성립하는 근거이며, 동시에 밸런스 귀속의 축이 된다. 합성 카드에서 `favor(patron)`은 **두 신 중 낮은 쪽**을 가리킨다 — 두 총애를 유지해야 얻은 카드이므로 약한 쪽이 기준이 되는 것이 일관된다.

`target`은 `self` · `enemy` · `all_enemies` 중 하나로 고정된 열거형이다(R-6.2). 그 외의 값은 즉시 반송한다. 좌표·인접·범위 지정 필드는 존재하지 않는다.

`tags`는 닫힌 어휘다: `attack` `defend` `utility` `multi` `token` `favor` `exhaust`.
`exhaust`는 DSL 연산자가 아니라 태그다(R-7.3). 기대값 환산에서 할인 계수를 받는다(T-6).

스키마는 LLM에게 주는 계약서다. 허용 op, 토큰 어휘, 수치 범위, 필수 필드, 태그 어휘를 여기서 닫는다. 스키마가 느슨하면 검증 게이트가 무력해진다.

### T-3.2 신 정의 스키마

```json
{
  "id": "zeus",
  "name": "제우스",
  "tokens": ["shock"],
  "ops": ["chain"],
  "rivals": ["poseidon"],
  "stage_effects": {
    "devotion": {
      "on_encounter_start": {
        "op": "apply_token", "token": "shock", "stacks": 1, "target": "all_enemies"
      }
    },
    "wrath": {
      "on_encounter_start": {
        "op": "apply_token", "token": "shock", "stacks": 2, "target": "self"
      }
    }
  },
  "demands": ["demand_zeus_overkill", "demand_zeus_multi"]
}
```

`stage_effects`가 총애와 역린의 전역 효과다(R-3.1). 평온과 노여움 단계에는 전역 효과가 없으므로 항목이 없다.

`ops`는 그 신에 귀속된 연산자다. 현재 `chain`(제우스)뿐이며, 대부분의 신은 빈 배열이다. 파급은 상태가 아니라 그 자리에서 끝나는 효과라 토큰이 될 수 없지만 귀속은 필요하다(R-4.1).

검증 게이트는 `token`과 `op`가 해당 신의 `tokens` · `ops`에 속하는지 확인한다 — **어휘 귀속은 전역 효과에도 적용된다.**

#### 전역 상수는 `gods.json`에 두지 않는다

**`favor_initial` · `favor_decay_per_encounter` · `favor_neglect_penalty` · 단계 경계 · 요구 보상과 페널티 · 은총 마일스톤 · 업그레이드 +50%는 전부 `core/favor.ts`의 상수다.**

이유는 하나다. 모든 신에게 동일하게 적용되는 값을 신별 데이터로 두면 **생성 단계에서 신마다 다른 값이 나온다.** 제우스만 `favor_initial: 55`인 `gods.json`이 나오면 조합별 승률 행렬(T-9.2)이 오염되고, 게이트는 이를 잡지 못한다 — 스키마상 유효한 값이기 때문이다. 마일스톤을 상수로 둔 것과 같은 논리이며, 같은 논리가 적용되는 필드를 데이터에 남겨둘 이유가 없다.

부수 효과로 R-3.1의 4단계 경계 중 평온·노여움 경계(30)가 스키마 어디에도 없던 문제가 사라진다. 단계 경계는 4개가 한 곳에 모여 있어야 한다.

이 값들은 S-5의 가정치이자 T-6 ⑤의 전역 파라미터이므로 자동 조정 대상이 아니고, 사람이 바꾸면 `human_intervened`와 `global_param_version`에 남는다.

**총애와 역린이 같은 스키마 형태로 표현된다는 것이 이 설계의 요점이다.** `target`을 `all_enemies`와 `self` 사이에서 뒤집으면 그 신의 권능이 방향을 바꾼다. 새 연산자도 새 토큰도 필요하지 않으므로 통과율에 영향이 없다.

### T-3.3 적 스키마

```json
{
  "id": "enemy_shade_warden",
  "name": "망령 감시자",
  "region": "underworld",
  "tier": "normal",
  "role": "attrition",
  "hp": 46,
  "intent_visible": true,
  "pattern": [
    { "op": "damage", "value": 6 },
    { "op": "apply_token", "token": "soaked", "stacks": 2 },
    { "op": "damage", "value": 4, "repeat": 2 }
  ],
  "pattern_mode": "cycle",
  "groups": [
    { "id": "grp_warden_solo", "with": [] },
    { "id": "grp_warden_thralls", "with": ["enemy_bone_thrall", "enemy_bone_thrall"] }
  ]
}
```

`tier`는 `normal` 또는 `boss`다. 보스는 `groups`를 갖지 않고 단독 조우로만 등장하며, 별도의 수치 범위를 적용받는다(T-6).

`role`은 닫힌 어휘다: `pressure`(고피해 저HP) · `attrition`(저피해 고HP) · `applier`(토큰 부여) · `bulwark`(방어 보유). 역할이 있어야 조우 편성이 의미를 갖고, 봇의 대상 선택 정책(T-6)이 편향되는지 역할별로 확인할 수 있다.

**`intent_visible`을 true로 고정한다.** 의도가 공개되면 룰 봇의 방어 정책이 산술로 확정된다 — 합산 피해만큼 block을 쌓는다는 규칙에 해석의 여지가 없다. 비공개면 정책이 기대값 추정을 포함하게 되고, 추정 방식을 바꿀 때마다 계기가 흔들려 이전 회차 데이터가 무효가 된다. 이는 플레이 편의가 아니라 **계기의 안정성 요건**이다. block이 턴 시작 시 소멸하는 규칙(R-7.2)과 맞물려 방어량이 일의적으로 결정된다.

복수 적에서는 각 적의 의도가 개별 공개된다. 봇은 적별 의도를 합산해 치사 위험을 판정한다.

`pattern_mode`는 `cycle`(순환) 또는 `conditional`(HP 임계 등)만 허용한다. 무작위 패턴은 승률 분산을 키우므로 초기 범위에서 제외한다(B-2).

### T-3.4 조우 구성

조우 하나에 어떤 적이 몇 마리 나오는지를 정의하는 문제다. 조우당 적이 1~3체가 되면서 필요해졌다.

**적 스키마 안의 `groups` 필드로 정의한다.** 각 적이 "나는 이런 편성으로 등장한다"를 스스로 갖는다. 별도 `encounters.json`을 두지 않는다.

근거는 생성 대상의 수다. 조우 파일을 분리하면 검증 게이트가 관리할 콘텐츠 종류가 하나 늘고, 통과율 지표가 종류별로 쪼개져 관리 비용이 붙는다. 조우 편성이 적 정의와 독립적으로 생성되어야 할 필요가 실제로 관측되면 그때 분리한다(B-2).

`with: []`는 단독 조우를 뜻한다. 게이트는 각 `group`의 총 HP와 총 의도 피해가 구역별 허용 범위(T-6) 안에 있는지 확인한다 — **조우 단위 임계값이 개체 단위 임계값보다 우선한다.**

### T-3.5 신의 요구 스키마

```json
{
  "id": "demand_zeus_multi",
  "patron": "zeus",
  "condition": "hit_targets_in_turn >= 3",
  "axis": "target_spread",
  "polarity": "+",
  "min_enemies": 3
}
```

요구는 전투 조우 진입 시 제시되고 해당 전투 안에서 판정된다.

**`reward`와 `penalty` 필드는 존재하지 않는다.** 보상 +12와 페널티 −18 / −9는 요구별 데이터가 아니라 `core/favor.ts`의 전역 상수이고(R-5.1), 페널티 대상은 신 id가 아니라 **나머지 후원 신**으로 런타임에 해석된다.

이 필드를 데이터에 두면 두 가지가 동시에 깨진다.

1. **페널티가 증발한다.** `penalty.god`에 라이벌 신 id를 박아두면, 그 신이 후원되지 않은 런에서는 페널티를 받을 대상이 없다 — 후원하지 않은 신은 등장하지 않고 호의도 추적되지 않는다(R-2.2). 라이벌 조합은 10개 중 2개뿐이므로 나머지 8개 조합에서 요구가 대가 없는 순수 이득이 되고, R-3의 저울 전체가 작동하지 않는다
2. **값이 요구마다 달라진다.** LLM이 `value: -14`인 요구를 생성해도 스키마상 유효하므로 게이트가 통과시킨다. 조합별 승률 비교의 전제가 깨진다

런타임 해석 규칙은 R-5.1의 표다: 라이벌 −18, 비라이벌 −9, 아르테미스가 포함된 조합은 페널티 없음.

**`axis` + `polarity`가 상충 판정의 형식이다.** 같은 `axis`에 반대 `polarity`를 가진 두 요구는 동시 만족이 불가능한 쌍으로 취급된다(R-5.2). 조우 진입 시 상충 요구를 제시할 때 이 쌍에서 뽑는다.

축 어휘는 닫힌 집합이다.

| `axis` | `+` | `−` |
|---|---|---|
| `target_spread` | 다중 대상 타격 | 단일 대상 집중 |
| `damage_taken` | 피해를 감수 | 무피해 유지 |
| `turn_economy` | 장기전 | 속결 |
| `token_load` | 토큰 다중 부여 | 토큰 없이 처리 |

검증 게이트는 (1) `axis`가 어휘에 있는지, (2) `polarity`가 `+`/`−`인지, (3) 같은 `axis`·반대 `polarity` 요구가 라이벌 신 쪽에 최소 1개 존재하는지 확인한다. 셋째 조건이 없으면 상충 쌍을 만들 수 없는 요구가 생산되고, 상충 요구 발생률이 설정값에 미달한다.

**라이벌이 없는 신의 요구는 조건 (3)을 면제한다.** 아르테미스는 `rivals: []`이므로 이 조건을 구조적으로 만족할 수 없고, 면제하지 않으면 아르테미스 요구가 전량 반송되어 R-9가 요구하는 신당 3~4종을 채울 수 없다. 규칙상으로도 모순이 없다 — 아르테미스 포함 조합에서는 상충 요구가 발생하지 않는다(R-5.2).

**`min_enemies`가 필요한 이유**는 `hit_targets_in_turn >= 3` 같은 조건이 적 1체 조우에서 달성 불가능하기 때문이다. 조건식과 `min_enemies`가 어긋난 요구는 생성 단계에서 반송된다.

**보스 조우에서는 `min_enemies <= 1`인 요구만 후보다.** 보스는 단독 조우이고(R-6.3) 보스에서도 요구가 제시되므로(R-5.1), 게이트는 각 신이 `min_enemies <= 1`인 요구를 최소 1개 갖는지 확인한다. 없으면 그 신이 제시하는 보스 요구 풀이 비어버린다.

S-4의 3번으로 적 수를 1체로 축소할 경우 `min_enemies > 1`인 요구는 전부 풀에서 제외된다.

## T-4. 효과 DSL

**공통 연산자**
`damage` `block` `draw` `energy` `heal` `self_damage` `apply_token` `favor_shift`

**귀속 연산자** — 신별로 귀속된다. 현재 하나뿐이다.

| 연산자 | 귀속 | 의미 |
|---|---|---|
| `chain` | zeus | 주 대상을 제외한 살아 있는 적 전원에게 `value`만큼 피해 |

`chain`은 `target: enemy` 카드에만 쓸 수 있다. 주 대상이 정의되지 않으면 "제외할 대상"이 없기 때문이며, 게이트가 이를 검사한다. 대상 선택 판단이 없어 결정론적이고 봇 정책이 단순해진다.

**토큰 어휘** — 닫힌 집합. 신별로 귀속된다. 각 토큰의 의미와 지속 규칙은 R-4.1에 있다.

```
zeus       shock
poseidon   displace  soaked
athena     bulwark  deflect
ares       bleed  frenzy
artemis    mark  crit
```

토큰은 주인공과 적 양쪽에 부여될 수 있다. 이 대칭성이 단계별 전역 효과(T-3.2)의 기구다.

**조건식** (`when`)
`favor(patron) >= n` · `favor(god) < n` · `has_token(target, t) >= n` · `turn > n` · `hp_pct(self) < n` · `deck_count(tag) >= n` · `enemy_count() >= n`

**어휘에 정의 없는 항목을 남기지 않는다.** `consume_token` 연산자와 `rival_active()` 조건식은 의미가 정의된 적이 없어 제거했다. 게이트가 검증해야 할 어휘에 의미 없는 항목이 있으면 LLM이 그것을 쓴 결과를 통과시킬지 반송할지 판정할 수 없다.

**공간 연산자는 존재하지 않는다.** 좌표, 인접, 열/행, 범위 형태를 표현하는 어휘를 추가하지 않는다(R-6.4).

**닫힌 토큰 어휘를 채택한 이유는 생성 품질이다.** 자유 서술 효과는 LLM이 그럴듯하지만 파싱 불가한 결과를 대량 생산한다. op와 토큰이 유한하면 검증 게이트가 정확해지고 통과율이 오르며, 그러면서도 토큰 간 상호작용(`soaked` + `shock`, `mark` + `crit`)에서 조합 깊이가 나온다. 깊이를 서술의 자유도가 아니라 어휘의 상호작용에서 얻는다.

DSL은 파싱 가능하고 정적 분석 가능해야 한다. 파싱 불가는 검증 실패로 처리한다.

## T-6. 단계별 계약과 밸런스 임계값

### ② LLM 대량 생성

- **신별로 나눠 생성한다.** 프롬프트에 해당 신의 토큰 어휘와 성향(R-4)만 노출하면 컨텍스트가 좁아지고 정합성이 올라간다
- 목표 수량의 5~10배를 과잉 생산한다. 통과율이 낮은 것은 실패가 아니라 정상 작동이다
- 적은 `role`과 `region`을 지정해 요청한다. 조우 편성 임계값을 맞추려면 역할 분포가 필요하다
- 요구는 `axis`·`polarity`를 명시적으로 지정해 요청한다. 라이벌 쌍의 축 균형을 맞춰야 상충 쌍이 성립한다(T-3.5)
- **합성 카드는 신별이 아니라 조합별로 생성한다.** 10개 조합에 각각 프롬프트가 필요하고, 프롬프트가 두 신의 토큰 어휘를 동시에 노출한다. 컨텍스트가 넓어지므로 통과율이 단일 신 카드보다 낮게 나올 것을 예상한다 — `pass_rate`를 조합별로 따로 기록한다
- 프롬프트는 `prompts/` 아래 파일로 관리하고 버전을 매긴다

### ③ 자동 검증 게이트

일곱 개의 필터를 통과해야 다음 단계로 간다.

| 필터 | `failure_breakdown` 키 | 판정 |
|---|---|---|
| 스키마 | `schema` | JSON Schema 위반, `patron`/`patron_pair` 동시 보유 또는 동시 누락, `target`·`tags`·`role` 열거형 이탈 |
| DSL 파싱 | `dsl_parse` | 효과식 파싱 실패, 미정의 op/토큰/조건 |
| 어휘 귀속 | `token_scope` | 소유 신에게 배정되지 않은 토큰 또는 연산자 사용 (`stage_effects` 포함), `target: enemy`가 아닌 카드의 `chain` |
| 합성 정합 | `fusion_scope` | `patron_pair` 정렬 위반, 두 신 외 어휘 사용, 한쪽 어휘만 사용, `exhaust` 태그 보유 |
| 요구 정합 | `demand_axis` | `axis` 어휘 이탈, 상충 쌍 부재(라이벌 없는 신은 면제), `condition`과 `min_enemies` 불일치, 신별 `min_enemies <= 1` 요구 부재 |
| 중복 | `duplicate` | op 시퀀스 + 수치 버킷 해시 일치, 또는 텍스트 코사인 유사도 0.85 이상 |
| 수치 이상 | `value_outlier` | 코스트당 기대값 또는 조우 임계값 이탈 |

**한쪽 어휘만 쓰는 합성 카드를 반송하는 것이 합성 정합 필터의 핵심이다.** LLM은 두 어휘를 주면 한쪽에 치우친 결과를 상당히 많이 만든다. 그런 카드는 조합에 귀속될 근거가 없고, 통과시키면 합성 카드가 그냥 강한 단일 신 카드가 된다.

### 코스트당 기대값이란

**카드 한 장이 에너지 1당 만들어내는 가치**를 하나의 수로 환산한 것이다. 단위는 "피해 1"이다. 피해 6을 주는 1코스트 카드와 방어 8을 주는 1코스트 카드를 같은 척도에서 비교하기 위한 장치이며, 게이트의 마지막 필터가 이 수를 본다.

```
가치 v =  1.0 × damage
        + 1.0 × chain × (평균 적 수 − 1)
        + 0.8 × block
        + 2.5 × draw
        + 3.0 × energy
        + 0.7 × heal
        − 1.2 × self_damage
        + Σ (토큰 가중치 × stacks)

토큰 가중치   shock 1.0 · displace 2.5 · soaked 0.8
             bulwark 1.0 · deflect 2.0 · bleed 1.5 · frenzy 1.5
             mark 2.0 · crit 3.0

코스트당 기대값 = v / max(cost, 0.5)
허용 범위 = 4.0 ~ 8.0
```

**토큰 가중치는 R-4.1의 지속 규칙을 전제로 한 값이다.** 조우 지속 토큰(`shock` `soaked` `frenzy` `mark`)은 남은 턴 수만큼 반복 적용되므로 소모형보다 높은 가중치를 받고, `bleed`는 스택이 매 턴 −1이므로 n스택의 총 피해가 n(n+1)/2다. 지속 규칙이 바뀌면 이 표 전체가 무효가 된다 — 가중치를 조정하기 전에 R-4.1을 먼저 본다.

`chain`은 토큰이 아니라 연산자이므로 가중치 표가 아니라 가치 식에 직접 들어간다. 파급 대상 수는 `평균 적 수 − 1`이며 초기값 1.0이다(`enemy_count_dist`로 갱신).

보정 규칙 넷.

- **조건부 효과**는 조건 발동률 추정치를 곱한다. 발동률은 ④의 시뮬 결과로 갱신한다 — 게이트는 회차가 늘수록 정확해진다
- **`all_enemies`**는 평균 적 수를 곱한다. 초기값 2.0이며 `enemy_count_dist` 실측으로 갱신한다. 이 계수가 없으면 광역 카드가 전량 반송되거나, 단일 대상 기준으로 평가되어 과대 성능이 통과한다
- **`exhaust` 태그**는 0.6을 곱한다. 런 1회만 쓰이므로 같은 가치라도 실효가 낮다. 이 할인이 없으면 강한 1회성 카드가 전부 반송된다
- **`favor(patron) >= 70` 조건**은 발동률이 플레이 스타일에 크게 의존한다. 총애 전역 효과(R-3.1)와 은총 획득(R-3.4)까지 걸린 단계이므로 고정 상수 대신 시뮬 기반 갱신이 특히 중요하다
- **합성 카드는 허용 범위가 다르다: 6.0 ~ 10.0.** 두 총애를 동시에 유지하고 카드 사용 조건까지 맞춘 대가이므로 일반 카드 상한(8.0)을 넘어야 한다. 이 범위를 일반 카드와 같게 두면 합성 카드가 보상으로 느껴지지 않는다
- **업그레이드는 기대값 계산에 포함하지 않는다.** +50%는 균일 규칙이므로 카드 간 상대 비교를 바꾸지 않는다. 대신 승률 영향은 `upgrade_rate`로 별도 관측한다

### 콘텐츠 분포 임계값

카드는 개별 기대값만 맞아도 풀 전체가 편향될 수 있다. 신별 풀에 아래 분포를 요구한다.

| 항목 | 목표 |
|---|---|
| 코스트 0 / 1 / 2 / 3 | 5% / 40% / 35% / 20% |
| `attack` / `defend` / `utility` | 40~50% / 20~30% / 25~35% |
| `exhaust` 비중 | 15% 이하 |
| 조건부 효과(`when`) 보유 비중 | 50% 이상 |

마지막 줄이 호의 시스템의 존재 조건이다. 조건부 효과가 절반 미만이면 호의 단계가 카드에 거의 영향을 주지 않고, `favor_curve`가 승률과 무관해진다.

### 적과 조우 임계값

**조우 단위 임계값이 개체 단위보다 우선한다.** 적 3체 조우는 각 적이 약해야 한다.

| 항목 | 지하 | 지상 |
|---|---|---|
| 조우 총 HP (`HP + bulwark`) | 40~90 | 90~170 |
| 조우 총 의도 피해 / 턴 | 8~14 | 14~22 |
| 조우당 적 수 | 1~2 | 2~3 |
| 보스 HP | 130 | 190 |
| 보스 의도 피해 / 턴 | 12~16 | 18~24 |
| 목표 전투 길이 | 3~5턴 | 4~6턴 |
| 허용 손실 (전투) | 약 12 | 약 18 |
| 허용 손실 (보스) | 약 30 | 약 40 |

조우 총 HP는 `bulwark`를 포함한 실효 HP다(R-7.2). 아테나 역린이 모든 적에게 `bulwark` 5를 주므로(R-3.1) 이를 빼고 판정하면 임계값이 실제 전투 길이를 예측하지 못한다.

허용 손실은 R-8.3의 HP 예산에서 역산한 값이다. 두 문서의 숫자가 어긋나면 R-8.3이 기준이다.

**S-4의 3번(휴식 노드 제거)을 실행하면 이 표를 함께 내려야 한다.** 휴식 0회는 HP 예산 160에 예상 손실 220으로 완주 불가다(R-8.3). 축소 시 허용 손실을 전투 8 / 12, 보스 20 / 28로 내리고 조우 총 HP와 의도 피해를 그에 맞춰 재산정한다. 그 시점 이전의 승률 데이터는 비교 대상이 아니다.

### 승률 대역 — 목표가 아니라 분별력 조건

**룰 봇의 절대 승률은 게임의 품질 지표가 아니다.** 봇은 고정된 단일 전략을 실행하는 계기이며, 계기가 게임을 잘 플레이할 이유는 없다. 온도계가 따뜻해야 할 이유가 없는 것과 같다.

룰 봇 승률에 대역을 두는 이유는 다른 데 있다. **양극단에서는 델타 측정의 분별력이 사라진다.**

| 항목 | 대역 | 대역을 벗어났을 때의 의미 |
|---|---|---|
| 룰 봇 전체 승률 | 15~70% | 0%에 가까우면 모든 런이 같은 곳에서 끝나 카드별 델타가 나오지 않는다. 100%에 가까우면 어떤 카드를 넣어도 이겨서 역시 델타가 나오지 않는다 |
| 조합별 승률 표준편차 | 8%p 이하 | 초과 시 특정 조합이 붕괴했거나 층화가 깨졌다 |
| 라이벌 − 비라이벌 (룰 봇) | −5 ~ −15%p | 룰 봇은 은총 경로만 실행하므로 라이벌이 불리해야 정상이다 |
| 라이벌 − 비라이벌 (LLM 에이전트) | 룰 봇보다 좁혀질 것 | 두 경로를 판단할 수 있는 주체에게만 라이벌의 상한이 열린다 |

**"사람에게 적절한 난이도인가"는 룰 봇이 답할 수 없는 질문이다.** 그 질문의 근거는 LLM 에이전트 런과 사람 플레이테스트다. 참고치로 30~50%를 두지만, 런 수가 수십이므로 카드 수치 정밀 조정의 근거로 쓰지 않는다.

**룰 봇의 본업은 상대 비교다.** 회차 간 변화, 카드 간 델타, 조합 간 격차. 이 셋은 계기가 서투른 채로 고정되어 있어도 정확하게 나온다. 계기가 회차마다 바뀌는 것만이 문제이며, 그래서 정책 버전 고정이 승률의 절댓값보다 중요하다.

### ④ 시뮬 — 세 층의 플레이어

| 주체 | 런 수 | 답하는 질문 |
|---|---|---|
| 룰 봇 | 수천 | 콘텐츠가 내부적으로 일관된가. 이상치가 있는가 |
| LLM 에이전트 | 수십 | 판단이 필요한 상태에 도달할 수 있는가. 선택이 선택인가 |
| 사람 플레이테스트 | 수 | 이 게임이 사람에게 적절한가 |

세 층은 대체 관계가 아니다. 룰 봇 없이는 카드 60장 × 조합 10칸의 델타를 채울 런 수가 확보되지 않고, 사람 없이는 난이도 판단의 근거가 없다. **각 층은 자기 질문에만 답하며, 다른 층의 질문에 대한 답으로 쓰이지 않는다.**

사람 플레이테스트 런도 계측에 남긴다. 런 수가 적어 통계가 되지 않지만, 기록되지 않으면 난이도 조정의 근거가 문서에 존재하지 않게 된다(T-9.3).

### 시나리오 시뮬 — 도달 불가능한 상태를 주입한다

룰 봇은 합성 카드에 도달하지 못하고 은총 6에 닿기 어렵다. 그러나 **그 상태를 측정하기 위해 봇이 거기까지 갈 필요는 없다. 초기 상태로 넣으면 된다.**

`sim/scenarios.ts`가 시작 상태를 오버라이드한다.

| 시나리오 | 주입 | 측정 대상 |
|---|---|---|
| `fused_deck` | 합성 카드를 시작 덱에 포함 | 합성 카드의 실제 성능과 `pick_rate` |
| `grace_4` | 은총 4 달성 상태 | 마일스톤 효과의 승률 기여 |
| `grace_6` | 은총 6 달성 상태 | 코스트 감소의 승률 기여 |
| `wrath_entry` | 한 신을 호의 5로 시작 | 역린 개입의 강도가 적정한지 |
| `devotion_hold` | 한 신을 호의 90으로 고정 | 총애 전역 효과의 강도 |
| `both_devotion` | 두 신을 호의 75로 시작 | 합성 조건이 실제로 어려운지 |

전부 시작 상태 변경이므로 `core/`를 건드리지 않고 결정론과 재현성이 유지된다(I-1, I-2). 계측에 `scenario` 필드로 표시하고, **시나리오 런은 기본 승률 집계에서 제외한다** — 섞으면 `win_rate_matrix`가 오염된다.

**주입이 자연 발생보다 더 나은 측정이다.** 자연 발생 런에서 합성 카드의 성능은 "합성에 도달할 만큼 잘 플레이했다"는 사실과 뒤섞인다. 주입하면 카드 자체의 기여만 분리된다. 조합 교락을 통제하는 것(T-7)과 같은 논리다.

### 룰 봇 정책 정의

**봇은 측정 대상이 아니라 측정의 렌즈다.** 정책이 명시되지 않으면 승률 수치가 무엇의 함수인지 정의되지 않는다.

| 판단 | 정책 |
|---|---|
| 카드 사용 순서 | 기대 가치 내림차순. 가치 = 예상 피해 + 예상 방어 환산 + 토큰 기대 이득 |
| 대상 선택 | 이번 턴에 처치 가능한 적이 있으면 그 적. 복수면 의도 피해량이 큰 적. 없으면 최저 HP |
| 광역 판단 | 살아 있는 적이 2체 이상이면 `all_enemies` 카드의 기대 가치에 적 수를 곱해 비교 |
| 방어 판단 | 공개된 적 의도(T-3.3)를 합산해 이번 턴 피해량을 구하고, 그만큼만 block을 쌓는다. 초과 방어는 낭비로 계산 |
| 치사 대응 | 합산 피해가 현재 HP 이상이면 모든 판단을 무시하고 방어 최대화 |
| 역린 회피 | 호의 15 이하 신이 있으면 그 신 카드에 최대 가중치. 치사 대응보다 낮고 그 외 모든 판단보다 높다 |
| 호의 관리 | 노여움 진입 예상 시 해당 신 카드에 가중치 부여 |
| 은총 경로 | 호의가 더 높은 신 하나를 총애로 유지하는 것을 목표로 한다. 두 신을 동시에 70 이상으로 올리려 시도하지 않는다 |
| 합성 시도 | 하지 않는다. 두 신이 우연히 70 이상이 되면 그 조우에서 양쪽 카드를 2장씩 쓰도록 순서만 조정한다 |
| 은총 마일스톤 선택 | 업그레이드·코스트 감소 대상은 코스트당 기대값 최상위 카드 |
| 상충 요구 선택 | 각 요구의 (달성 확률 × 12)에서 상대 신의 예상 하락 손실(라이벌 −18 / 비라이벌 −9)을 뺀 값을 비교. 상대 신을 역린으로 밀어넣는 선택지에는 고정 감점 |
| 요구 수락 | 요구는 거절 불가(R-5.1). 달성 시도 여부만 판단한다 |
| 층 경로 선택 (3·5층) | HP가 최대의 50% 미만이면 휴식. 그 외에는 전투 |
| 휴식 선택 | HP가 최대의 70% 미만이면 회복. 아니면 코스트당 기대값 최하위 카드 제거 |
| 보상 선택 | 현재 덱의 태그 분포에서 가장 부족한 축을 보완 |
| `exhaust` 취급 | 기대 가치에 0.6을 곱해 순서를 정한다 |
| 탐색 깊이 | 1턴 그리디. 다중 턴 탐색 없음 |

**정책이 단일 전략인 것은 결함이 아니라 정의다.** 룰 봇은 은총 경로만 실행하고 합성을 노리지 않는다. 여러 조우에 걸친 계획은 1턴 그리디로 세울 수 없고, 억지로 휴리스틱을 넣으면 그 휴리스틱의 품질이 승률의 지배 변수가 된다. 합성 카드의 성능은 시나리오 주입으로 측정한다.

**고정된 단일 전략이 오히려 두 개의 측정을 만든다.**

- `fusion_rate`가 룰 봇에서 0에 가깝고 LLM 에이전트에서 유의하게 높으면, 그것이 "판단할 수 있는 주체에게만 열리는 경로가 실재한다"는 직접 증거다
- 라이벌 조합의 승률 격차가 두 주체에서 좁혀지는 기구도 같은 곳이다. 라이벌 조합은 합성이 가장 어렵고 은총이 가장 빠르므로, 두 경로를 저울질할 수 있어야 상한이 열린다

**봇의 실력을 올리는 것은 답이 아니다.** 탐색 깊이를 2턴 이상으로 늘리면 수천 런에 계산 비용이 그대로 곱해지고, 무엇보다 정책을 바꿀 때마다 이전 회차 데이터가 전부 무효가 된다. 서투른 채로 고정된 계기가 똑똑하지만 흔들리는 계기보다 낫다.

**층 경로와 휴식 선택은 임계값 두 개(50%, 70%)로 고정했다.** 이 값이 정책의 일부이므로 바꾸면 정책 버전이 올라간다.

**정책 버전은 고정하고 기록한다.** 정책을 바꾸면 이전 회차의 밸런스 결론이 모두 무효가 된다. v1으로 튜닝한 뒤 v2로 개선하면 v1 시점의 조정이 근거를 잃는다. 정책을 개선할 경우 이전 데이터를 폐기하고 처음부터 재수집하며, 그 사실을 계측에 남긴다. **계기의 절대 성능보다 계기의 불변성이 중요하다.**

### ⑤ 리포트 → 자동 조정

- 임계 이탈 카드의 수치를 자동 조정하고 재시뮬한다
- 3회 조정 후에도 이탈하면 폐기하고 ②에 재생성을 요청한다
- 회차별 승률 분산 추이를 보관한다
- **전역 파라미터는 자동 조정 대상이 아니다.** 호의 변동량(R-3.3), HP와 회복량(R-7.1, R-8.2), 에너지·드로우는 하나를 바꾸면 모든 카드의 조건 발동률이 변하고 이전 회차 데이터가 무효가 된다. 봇 정책과 같은 취급으로 사람이 명시적으로 변경하고 계측에 남긴다

**조정 순서가 있고, 근거로 삼는 주체가 단계마다 다르다.**

| 순서 | 조정 대상 | 근거 |
|---|---|---|
| 1 | 임계값을 벗어난 적·조우 수치 | 룰 봇. 임계값 위반은 절대 기준이라 계기만으로 판정된다 |
| 2 | 카드 간 상대 델타 이상치 | 룰 봇. 상대 비교가 계기의 본업이다 |
| 3 | 전역 파라미터 (HP 예산, 호의 변동량) | **LLM 에이전트와 사람 플레이테스트.** 룰 봇 승률은 이 판단의 근거가 되지 못한다 |

3을 룰 봇 승률로 판단하면 계기의 서투름을 게임의 난이도로 오독한다. 반대로 1과 2를 소수의 사람 런으로 판단하면 표본이 부족하다. **단계마다 답할 수 있는 주체가 정해져 있다.**

룰 봇 승률이 분별 대역(15~70%)을 벗어나면 그것은 난이도 신호가 아니라 **측정 불능 신호**다. 이때는 게임을 조정하기 전에 대역 안으로 되돌려 놓아야 하며, 그 조정은 3번에 해당하므로 사람이 판단하고 계측에 남긴다.

## T-7. 조합 교락의 통제

**인지된 위험**: 카드 성능이 어떤 신 조합에서 플레이되었는지에 의존하므로, 카드별 승률 델타가 조합 효과와 섞인다. 이를 방치하면 자동 조정이 잘못된 대상을 건드린다. 상충 요구가 라이벌 조합에만 발생하고(R-5.2) 단계별 전역 효과가 신마다 다르므로(R-3.1) 이 교락은 더 강해졌다.

**통제 방법**

1. **층화 시뮬** — 10개 조합에 런을 균등 배분한다. 조합을 무작위로 뽑지 않는다
2. **조합 내 델타 측정** — 카드 승률 델타는 조합 내에서 계산한 뒤 조합 간 평균을 낸다. 전체 풀에서 한 번에 계산하지 않는다
3. **조정 대상 분리** — 특정 조합에서만 이탈하는 카드는 카드 수치가 아니라 조합 상호작용 문제로 분류하고, 카드 자동 조정 대상에서 제외한 뒤 별도 보고한다
4. **기준선 활용** — 아르테미스 포함 조합을 대조군으로 둔다. 상충 요구도 없고 라이벌 페널티도 없으므로 호의 압력의 순효과가 여기서 분리된다

조합 수를 10으로 닫은 것(R-9)과 조합이 런의 불변량인 것(I-7)이 이 통제의 두 전제다. 조합이 늘거나 런 중에 바뀌면 층화가 무의미해진다.

## T-8. LLM 에이전트 루프

플레이테스트 에이전트는 사람 플레이어와 동일한 인터페이스를 사용한다. 별도의 전용 API를 주지 않는다.

```
관측         현재 상태를 사람이 보는 정보 범위로 직렬화
             (호의 수치와 단계, 적별 의도, 제시된 요구, 남은 층 포함)
컨텍스트 압축   전체 로그가 아니라 요약 + 최근 N턴
판단         가능한 action 목록 중 선택 + 선택 이유
행동         core에 dispatch
폴백         파싱 실패·무효 action·타임아웃 → 룰 봇 판단으로 대체, 실패 카운트 기록
```

action에는 대상 지정과 층 경로 선택이 포함된다. `enemy` 카드의 action은 카드 id와 대상 적 index를 함께 갖는다. 존재하지 않는 index나 이미 처치된 적을 지정하면 무효 action으로 처리하고 폴백한다.

**에이전트에게 특히 물어야 할 것은 호의 관리의 체감이다.** 상충 요구에서 어느 쪽을 왜 택했는지, 역린이 회복 불가능하게 느껴진 시점이 있었는지, 휴식과 전투 사이 선택이 실제로 고민이었는지는 통계로 나오지 않는다. 선택 이유를 로그에 남기는 목적이 여기에 있다.

에이전트가 사람과 같은 인터페이스를 쓰는 것은 계측 정합성 문제다. **에이전트는 세 층 중 사람의 판단을 근사하는 유일한 층이므로**, 특권 정보를 주면 그 근사가 무의미해진다. 룰 봇에는 이 제약이 필요 없다 — 계기는 무엇을 보든 고정되어 있기만 하면 된다.

### T-9.2 주요 지표

**신 조합 승률 행렬** — 5×5 히트맵. 읽는 대상은 칸의 절댓값이 아니라 **칸 사이의 차이**다. 라이벌 조합과 비라이벌 조합의 격차가 T-6의 대역에 있는지 확인한다. 이 행렬이 조합 밸런싱의 유일한 근거다.

**두 봇의 조합 격차 차이** — 룰 봇과 LLM 에이전트에서 라이벌 조합의 불리함이 다르게 나타나는지. 좁혀지지 않으면 R-4의 고위험 고상한 설계가 실패한 것이다.

**은총과 합성의 조합별 순서** — R-3.6의 표가 예측한 순서(은총은 라이벌 > 비라이벌 > 대조군, 합성은 그 역순)가 `grace_earned`와 `fusion_rate`에서 나와야 한다. 순서가 어긋나면 라이벌 조합의 높은 상한이 실재하지 않는 것이고, R-4의 설계 의도가 실패한 것이다.

**주체별 `fusion_rate` 차이** — 룰 봇은 합성을 노리지 않는다(T-6). 이 값이 룰 봇과 LLM 에이전트에서 비슷하면 합성 조건이 너무 쉬워 우연히 달성되고 있다는 뜻이며, 조건을 조여야 한다.

**시나리오 런과 기본 런의 대비** — `fused_deck`과 기본 런의 승률 차이가 합성 카드의 순수 기여다. 이 차이가 작으면 합성 카드가 보상으로서 약하고, 기대값 범위(6.0~10.0)를 다시 봐야 한다.

**호의 곡선** — 곡선이 평탄하면 호의 시스템이 작동하지 않는다는 뜻이고, R-3을 다시 설계해야 한다는 신호다. 조건부 효과 보유 비중(T-6)이 낮을 때도 같은 증상이 나온다.

**역린 체류 비율과 복귀율** — `wrath_recovery`가 0에 가까우면 역린이 사실상 사망 선고이므로 R-3.3의 상승량을 올려야 한다. 반대로 1에 가까우면 역린이 위협이 아니다. **이 비율이 "호의 관리가 게임을 어렵게 만든다"는 설계 의도가 실제로 성립하는지를 판정하는 지표다.**

**HP 곡선과 구역 도달률** — R-8.3의 HP 예산이 맞았는지 보는 직접 지표. 지하 도달률이 100%인데 지상 클리어율이 5% 미만이면 예산이 지상 구역에서 붕괴한 것이고, 카드가 아니라 전역 파라미터를 고쳐야 한다.

**휴식·경로 선택 분포** — `rest_choices`와 `path_choices`가 한쪽으로 완전히 치우치면 R-8.2의 3자 선택이 선택이 아니다. 회복만 고르면 카드 제거의 값이 낮고, 전투만 고르면 HP 압력이 부족하다.

**상충 요구 선택 분포** — 한쪽으로 크게 치우치면 두 축의 요구 난이도가 비대칭이라는 뜻이다. 저울이 한쪽으로 기울어 있으면 선택이 아니다.

**방어 효율** — `block_efficiency`가 1에 가까우면 봇이 의도를 정확히 읽고 있다는 뜻이다. 크게 낮으면 초과 방어로 자원을 낭비하고 있고, 승률이 봇의 미숙함 때문에 낮은 것이다.

**대상 사용 분포** — `target_spread`가 치우치면 대상 선택이 판단이 아니다. 광역이 항상 우세하면 환산 계수가 낮고, 단일 대상만 쓰이면 적 수 분포가 얇다.

### T-9.3 정직성 요건

`human_intervened`와 `ai_failures`는 비워두지 않는다.

파이프라인이 완전 자동으로 돌았다는 서술은 거짓이거나, 아무도 어려운 것을 시도하지 않았다는 뜻이다. 어디서 AI가 틀렸고 어디서 사람이 들어갔는지가 기록되어야 이 프로젝트의 계측이 신뢰할 수 있는 것이 된다. 성공 사례만 남은 로그는 데이터가 아니라 홍보물이다.

전역 파라미터 조정은 전부 `human_intervened`에 남는다(T-6 ⑤). HP 예산을 사람이 고쳤다는 기록이 없으면 그 승률 개선은 파이프라인의 성과로 오독된다.

**사람 플레이테스트 런도 남긴다.** 런 수가 적어 통계가 되지 않지만, 전역 파라미터 조정의 근거가 바로 이 런들이다. 기록하지 않으면 난이도 판단이 어디서 왔는지 문서에 존재하지 않게 되고, "루프가 콘텐츠를 수렴시켰다"는 서술에 사람의 개입이 숨는다.
