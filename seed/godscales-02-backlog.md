# 신들의 저울 — 후속 백로그

`godscales-02-backlog.md` · 문서 세트: 01 시드 / **02 후속 백로그(현재)** / 03 게임 규칙 / 04 기술 설계

**이 문서의 용도**
본편에 넣고 싶은 충동이 생길 때 여기에 적고 넘어간다. 그것이 이 문서의 유일한 기능이다.
백로그가 있어야 동결이 지켜진다. 적을 곳이 없으면 코드에 들어간다.

**기록 형식**
항목 / 왜 지금 안 하는가 / 착수 조건. 세 번째 칸이 비어 있으면 그 항목은 아직 백로그에 들어올 자격이 없다.

---

## B-0. 승격 조건 (공통)

아래를 **모두** 만족하기 전에는 어떤 항목도 본편으로 올리지 않는다.

1. 축소 우선순위(S-4)에서 버린 것이 없다
2. 파이프라인 루프가 3회차 이상 안정적으로 완주한다
3. 승률 분산이 회차마다 줄어드는 것이 데이터로 확인된다
4. 배포본으로 1런 완주가 매일 재확인되고 있다

**이 네 개가 충족되지 않은 상태에서 백로그를 여는 것이 이 프로젝트의 가장 큰 실패 경로다.**

---

## B-1. 본선 대비 (최우선 그룹)

사전과제 이후 가장 값이 큰 묶음. 본선 산출물이 *게임 프로토타입 + AI 에이전트 설계서 + 디렉팅 명세서*이므로, 이 항목들은 버려지는 작업이 아니다.

| 항목 | 왜 지금 안 하는가 | 착수 조건 |
|---|---|---|
| 런타임 LLM 에이전트 — 신을 대화 가능한 존재로 | I-1의 네트워크 접근 금지 위반. API 키 없는 정적 배포(T-1)도 성립하지 않는다 | 사전과제 제출 이후. 별도 브랜치에서만 |
| 디렉팅 명세서 초안 | 사전과제 요건이 아니다. 다만 `prompts/` 버전 관리가 그 기반이 된다 | 프롬프트 버전 이력이 3세대 이상 쌓인 뒤 |
| 주제 무관 코어 분리 | 이미 부분 달성. `core/`(T-2)가 신화 소재에 의존하지 않게 정리하는 작업 | 여유 시간 발생 시 즉시. 비용 낮고 이득 큼 |
| 에이전트 다중 페르소나 (공격적 / 신중한 플레이어) | 단일 페르소나의 `fusion_rate`가 룰 봇과 유의하게 다른지 먼저 확인해야 한다 | 주체별 격차가 한 번 관측된 뒤 |
| 룰 봇 정책 v2 (다중 턴 탐색) | 계기의 불변성이 절대 성능보다 중요하다. 정책을 바꾸면 이전 회차 데이터가 전부 무효가 된다 (T-6) | 콘텐츠가 동결되고 더 이상 회차를 돌릴 필요가 없어진 뒤. 사실상 보류 |

**주제 무관 코어 분리는 우선순위가 높다.** 본선은 주제가 현장에서 공개되므로, 전투 엔진과 파이프라인이 소재로부터 독립되어 있으면 48시간의 출발점이 달라진다.

## B-2. 게임 확장

| 항목 | 왜 지금 안 하는가 | 착수 조건 |
|---|---|---|
| 런 중 후원 신 교체 | I-7 위반. 측정 단위가 조합에서 조합 궤적으로 바뀌고 층화 시뮬(T-7)이 무의미해진다. 라이벌 압력이 회피 가능해져 조합 밸런싱의 근거가 사라진다 | 승률의 측정 단위를 조합이 아닌 궤적으로 재정의하고, 그 단위로 층화를 다시 설계할 수 있을 때. 사실상 보류 |
| 제3신의 일시적 축복 (후원 아닌 신의 단발 효과) | 요구 시스템이 아직 실측 검증되지 않았다. 콘텐츠 축이 하나 늘면 통과율 관리가 복잡해진다 | 요구 발생 빈도·강도가 시뮬로 확정된 뒤. 단, 조합 정체성과 보상 풀(R-10)을 건드리지 않는 형태로만 |
| 신 6~7명으로 확대 | 조합이 15~21칸이 되어 칸당 런 수가 얇아진다 (R-9) | 조합당 런 수를 유지하며 시뮬 처리량을 2배 이상 늘린 뒤 |
| `random_enemy` 대상 추가 | 승률 분산이 커져 이상치 탐지가 둔해진다. `pattern_mode: random`과 같은 이유 | 분산 기준선이 확보된 뒤 |
| 조우당 적 4체 이상 | 광역 카드의 기대값 환산 계수(T-6)가 아직 실측으로 보정되지 않았다 | `enemy_count_dist`와 `target_spread`가 안정된 뒤 |
| 유물 카테고리 | 카드만으로도 파이프라인 증명이 성립한다. 생성 대상이 늘면 통과율 관리가 복잡해진다 | 카드 통과율이 안정된 뒤 |
| 조우 구성을 별도 `encounters.json`으로 분리 | T-3.4에서 적 스키마의 `groups` 필드로 확정했다. 파일을 분리하면 게이트 대상이 하나 늘고 통과율 지표가 쪼개진다 | 조우 편성이 적 정의와 독립적으로 생성되어야 할 필요가 관측된 뒤 |
| 토큰의 신 간 교차 공유 | 조합 깊이는 늘지만 귀속 측정이 약해진다. 완전 귀속은 R-4.1에서 확정되었다 | 조합 교락 통제(T-7)가 실측으로 작동 확인된 뒤 |
| 역린 개입의 다단계화 (호의가 더 떨어지면 더 강한 개입) | 단일 임계 개입의 효과가 아직 실측되지 않았다. 지금 늘리면 어느 단계가 승률을 움직였는지 분리되지 않는다 | `wrath_recovery`와 역린 체류 비율이 안정된 뒤 |
| 상충 요구의 3축 이상 동시 발생 | 두 축 상충의 선택 분포가 아직 균형인지 확인되지 않았다 | `conflict_outcomes`가 한쪽으로 치우치지 않음이 확인된 뒤 |
| 무작위 적 패턴 (`pattern_mode: random`) | 승률 분산이 커져 이상치 탐지가 둔해진다 | 분산 기준선이 확보된 뒤 |
| 신의 요구 다양화, 서사 이벤트 | 시스템이 아니라 콘텐츠. 논지에 기여하지 않는다 | 게임 체감 개선이 병목이 될 때 |
| 메타 프로그레션 | 런 간 상태가 생기면 승률의 의미가 흐려진다 | 없음. 측정 논지와 충돌하므로 사실상 보류 |
| 3번째 구역 / 난이도 단계 | 1런 소요가 늘어 시뮬 처리량이 떨어진다 | 시뮬 처리량 여유 확보 후 |
| 상점·이벤트·보물 노드 | 노드 종류가 늘면 층 경로 선택이 봇 정책의 지배 변수가 된다. 휴식 노드 하나로도 선택 압력이 성립한다 (R-8.2) | `path_choices`가 한쪽으로 치우치지 않음이 확인된 뒤 |
| 카드별 개별 업그레이드 효과 | 균일 +50% 규칙(R-10.1)으로 이미 성립한다. 카드마다 다른 업그레이드를 만들면 생성 대상이 두 배가 되고 `card_win_delta`의 귀속 단위가 쪼개진다 | `upgrade_rate`와 카드 단위 델타가 안정된 뒤 |
| 휴식 노드에서 업그레이드 선택 (3택) | 은총 2가 이미 업그레이드 경로를 제공한다. 휴식에 세 번째 선택지가 붙으면 봇의 휴식 정책이 세 갈래가 되고 `rest_choices` 해석이 복잡해진다 | `rest_choices`가 2택에서 균형인 것이 확인된 뒤 |
| 합성 카드 조합당 2장 이상 | 조합별 생성 프롬프트 10개의 통과율이 아직 실측되지 않았다 | 합성 카드 `by_pairing` 통과율이 단일 신 카드와 비슷한 수준으로 올라온 뒤 |
| 신 해금 (런 간) | 승률을 오염시키지 않는다. `unlocked` 목록을 `core/` 밖에 두고 UI가 선택지를 필터링하면 I-1·I-2가 유지되며 시뮬은 항상 전체 해금으로 돌린다. 다만 사전과제에서는 심사자가 조합 10칸 히트맵을 보면서 게임에서는 일부 조합만 열려 있는 상태가 된다 | 사전과제 제출 이후 |
| 층 수 확대 / 분기 폭 확대 | HP 예산(R-8.3)이 아직 실측 검증되지 않았다 | `hp_curve`가 사람 플레이테스트 기준으로 검증된 뒤 |

**신 교체와 메타 프로그레션은 같은 등급이다.** 둘 다 재미의 축으로는 매력적이지만 승률의 의미를 훼손한다. 등재는 하되 승격은 기대하지 않는다.

## B-3. 파이프라인 강화

| 항목 | 왜 지금 안 하는가 | 착수 조건 |
|---|---|---|
| 조건 발동률의 베이지안 갱신 | 단순 빈도 갱신으로도 게이트가 작동한다 | 발동률 추정 오차가 오조정을 유발하는 것이 관측된 뒤 |
| 프롬프트 A/B 자동 선택 | 버전별 통과율은 이미 기록된다. 자동 선택까지는 과잉 | 프롬프트 세대가 5개 이상 쌓인 뒤 |
| 카드 일러스트 생성 파이프라인 | 시연 임팩트는 크지만 비용과 실패율도 크다. 텍스트 콘텐츠 루프가 먼저다 | 게임 루프와 파이프라인이 모두 안정된 뒤 |
| 밸런스 회귀 테스트 (CI) | 수동 실행으로 충분한 규모다 | 콘텐츠가 100개를 넘어 수동 확인이 불가능해질 때 |
| 생성 비용 최적화 (캐싱, 배치) | 현재 규모에서 병목이 아니다 | 생성 소요 시간이 루프 회차 수를 제약할 때 |

## B-4. 계측 및 표현

| 항목 | 왜 지금 안 하는가 | 착수 조건 |
|---|---|---|
| 시뮬 결과 웹 대시보드 | 리포트가 파일로 나오면 문서 작성에는 충분하다 | 여유 시간 발생 시 우선 착수 — 시연에 직접 쓰인다 |
| 조합 히트맵 인터랙티브 | 정적 이미지로도 논지가 전달된다 | 대시보드 착수 시 함께 |
| 프롬프트 diff 뷰어 | git으로 충분하다 | 사실상 불필요 |
| 호의 곡선 실시간 표시 (게임 내) | UI 비용. 다만 시연 가독성에는 기여한다 | 게임 기능 동결 이후 표현 개선 단계에서 |

**대시보드는 이 그룹에서 유일하게 우선순위가 높다.** 파이프라인이 실제로 돌았다는 사실을 보여주는 가장 빠른 수단이다.

## B-5. 폴리시

전부 낮은 우선순위. 논지에 기여하지 않으며, 시간이 남는다는 보장이 없다.

사운드 · 전투 애니메이션 · 튜토리얼 · 모바일 레이아웃 · 접근성 · 다국어 · 세이브/로드

| 항목 | 왜 지금 안 하는가 | 착수 조건 |
|---|---|---|
| 새로고침 복구 (`localStorage`에 action 로그 누적) | 저장할 상태가 없도록 설계했고(T-1.1), 이것을 열면 "런 간에 무엇을 남길까"가 따라 열린다. 그 방향은 B-6의 메타 프로그레션이다 | 시연 중 새로고침 사고가 실제로 발생했을 때. `localStorage.setItem`과 복원 한 줄씩이며 그 이상으로 키우지 않는다 |

이 중 착수 가치가 있는 것은 **전투 로그 가독성**뿐이다. 시연에서 무슨 일이 일어났는지 읽히게 만드는 작업이므로 폴리시가 아니라 전달의 문제다.

복수 적 도입으로 전투 로그의 가독성 요구가 올라갔다. 어느 적에게 무엇이 들어갔는지 읽히지 않으면 시연에서 대상 선택이 판단이었다는 사실이 전달되지 않는다.

## B-6. 여유가 생겨도 하지 않는 것

착수 조건이 없는 항목. 이 프로젝트의 논지에 기여하지 않거나 정면으로 충돌한다.

| 항목 | 이유 |
|---|---|
| 배치/슬롯 시스템, 격자 전투 | R-6.4에서 기각. 봇의 배치 휴리스틱이 승률의 지배 변수가 되고, DSL에 공간 어휘를 추가하면 통과율 전제가 무너진다 |
| 실시간 액션 전투 | 헤드리스 시뮬이 불가능해진다. 프로젝트의 전제가 무너진다 |
| 물리 엔진, 3D | `core/`의 순수성을 침식한다 |
| 온라인 멀티플레이 | 결정론과 재현성을 잃는다 |
| 게임 엔진으로 이식 | 브라우저·Node의 `core/` 공유라는 이득을 버린다 |
| 장르 변경 | 계측 가능성 때문에 선택한 장르다 |
| 런 간 영구 강화 (영구 HP, 시작 카드, 통화) | `win_rate`가 "몇 번째 런인가"의 함수가 된다. 층화 시뮬에 메타 진행도 축이 붙어 10칸이 10×N칸으로 늘고, 조합별 승률 행렬이 무의미해진다. 도입하려면 대표 지표를 승률에서 다른 것으로 바꾸고 01부터 다시 써야 한다 |
| 셋 이상의 신에 걸친 카드 귀속 | 5×5 행렬의 어느 칸에도 대응되지 않아 조합 내 델타 측정이 성립하지 않는다 (I-4) |
| 신화 외 소재 추가 | 어휘 귀속 구조가 흐려진다 |
| 소환물, 동료 캐릭터 | 주인공 1인 전제를 깬다. 격자 전투의 우회로로 등장하기 쉬우므로 명시해 둔다 |

## B-7. 항목 추가 규칙

- 착수 조건을 쓸 수 없으면 적지 않는다. 조건 없는 항목은 소원이지 백로그가 아니다
- "재밌을 것 같다"는 이유만으로는 등재하지 않는다. 논지에 어떻게 기여하는지 한 줄로 쓴다
- B-6에 해당하는 발상은 등재하지 않고 기각한다
- 이 문서에 적은 뒤에는 그 생각을 놓는다. 다시 꺼내는 시점은 B-0의 조건이 충족된 이후다
