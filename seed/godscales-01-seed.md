## S-1. 프로젝트 정의

**신들의 저울** — 올림포스 신들의 후원을 업고 지하와 지상을 되돌리는 로그라이크 덱빌더. 두 신의 호의를 저울질하는 것이 런의 전략이다.

호의는 축적하는 자원이 아니라 관리해야 하는 부채로 설계한다. 플레이어가 겪는 압박의 대부분을 전투가 아니라 저울질에서 나오게 한다. 기구는 R-3과 R-5에 있다.

**만드는 방식** — 게임 콘텐츠(카드·적·요구)를 LLM으로 생성하고, 자동 검증 게이트와 헤드리스 시뮬레이션 루프로 밸런싱한다. 사람은 스키마와 임계값을 정의하고 루프가 콘텐츠를 수렴시킨다. LLM은 빌드타임에만 관여한다.

**산출물은 둘이다.**
1. 플레이 가능한 게임
2. 그 게임이 만들어진 파이프라인과 계측 기록

특정 상용 게임의 캐릭터·고유 명명·시각 표현은 차용하지 않는다. 참조 대상은 신화 자체다.

## S-2. 불변 조건

**I-1. 게임 로직은 순수하다**
`core/`는 `(state, action) → state` 형태의 결정론적 전이만 갖는다. `Math.random()` · `Date.now()` · DOM · 파일 · 네트워크 접근을 금지한다. 런타임 LLM 호출을 포함한다.

**I-2. 모든 플레이는 재현 가능하다**
`seed + action[]`으로 임의의 런을 복원한다. 난수는 시드 기반 PRNG를 통해서만 얻는다. 룰 봇 런은 `seed + policy_version`으로, LLM 에이전트 런은 action 로그 전체로 재현한다. 두 경우를 `replay_mode`로 구분해 기록한다.

**I-3. UI는 상태를 변경하지 않는다**
`ui/`는 `core/`를 읽고 action을 dispatch한다. UI를 제거해도 게임은 완주 가능하다.

**I-4. 모든 카드는 소유 귀속을 갖는다**
카드는 단일 신(`patron`) 또는 두 신 조합(`patron_pair`) 중 정확히 하나를 갖는다.

**I-5. 콘텐츠는 게이트를 통과해야 빌드에 들어간다**
사람의 개입은 스키마·임계값·프롬프트 수정으로 한정한다. 예외는 `human_intervened`로 기록한다.

**I-6. 파이프라인 로그는 누적 보관한다**
생성 시도, 반송, 시뮬 결과를 모두 남긴다.

**I-7. 조합 정체성은 런의 불변량이다**
런 시작 시 확정된 신 조합은 런이 끝날 때까지 유지한다(R-2).

## S-4. 축소 우선순위

리소스가 부족할 때 위에서부터 버린다.

1. UI 완성도 (배치·장식 연출·트랜지션)
2. 지상 구역 → 지하 1구역만
3. 층 분기 → 3·5층을 전투로 고정, 휴식 노드 제거 (R-8)
4. 조우당 적 수 → 1체 고정 (R-6.3)
5. 상충 요구 → 조우당 요구 1개 (R-5.2)
6. 합성 카드 → 은총 경로만 유지 (R-3.5)
7. 은총 마일스톤 → 2·4만 유지 (R-3.4)
8. 총애 전역 효과 → 카드 `when` 조건만 유지 (R-3.1)
9. 역린 단계 → 노여움으로 통합 (R-3.1)
10. 은총 전체 → 총애는 카드 변조만 (R-3.4)
11. 신 5명 → 4명 (조합 6개)
12. 요구 시스템 → 호의는 카드 사용·감쇠로만 변동
13. LLM 에이전트 → 룰 봇만 유지
14. 호의 변조 → 순수 카드 전투

**파이프라인은 어떤 경우에도 유지한다.** 게임을 줄여 파이프라인을 지킨다.

**1번에서 버리는 것은 장식으로 한정한다.** 어느 적에게 무엇이 들어갔는지와 `chain` 파급 여부를 보여주는 연출은 유지한다. 판정 기준은 A-2.6의 빈도 표이며, 반복 빈도가 높은 것부터 버린다.

**3번을 실행할 때는 T-6의 허용 손실을 전투 8 / 12, 보스 20 / 28로 함께 내리고** 적·조우 수치를 재산정한다. 그 시점 이전의 승률 데이터는 비교에서 제외한다.

**이 값들은 `core/`의 상수로 둔다**(T-3.2).
